# OpenCalque: architecture and handoff

This document is for whoever continues the project, human or AI, starting cold. It records what exists, why it is built this way, how to extend it, what is unverified, and what to do next. The [README](../README.md) covers usage and the file format from a user's point of view; this covers the inside.

Last updated: 2026-11-06, after 1.5.0 (see §7 for how it is checked, and §4, "The file format and its versions"). The roadmap is in [FEATURES.md](FEATURES.md); what changed in each version is in the [changelog](../CHANGELOG.md).

**The project was renamed from OpenCAD to OpenCalque** (October 2026). What was made under the old name keeps working: `parseDocument` accepts `"format": "opencad"` and saves the new name, `.opencad` files open like `.opencalque` ones, the web app copies its settings to the new storage keys once (`apps/web/src/migrate.ts`, which must stay the first import), and the desktop app copies its old profile folder the first time it starts. The example plan in the README is `examples/apartment.opencalque`, generated by `pnpm example`; the screenshots are taken from it.

## 1. Goal and constraints

OpenCalque is a free, open-source 2D drawing tool for plans and layouts, comparable to SketchUp LayOut or synaps.app, with a Figma-like interface. The owner's requirements, in their words and order of emphasis:

- **Components are mandatory.** Reusable definitions with instances, plus importable component libraries.
- **Layers, walls, staircases** and similar architectural objects.
- **Extensible** through extensions.
- **Cross-platform, easy to run, open source, usable locally.** This is the main product.
- **An open, well-designed data model that AI workflows can digest.**
- **Later, possibly:** a hosted website offering multi-user collaboration and free hosting of a few projects. Not built, but the design must not block it.
- **The desktop shell technology is open.** Electron was chosen (see §8) but the owner explicitly did not want to prescribe it.

## 2. Running and checking

Requires Node 22+ and pnpm 9. All commands run from the repository root.

| Command | What it does |
| --- | --- |
| `pnpm install` | Install everything |
| `pnpm dev` | Desktop app with hot reload |
| `pnpm dev:web` | The editor in a browser at the URL Vite prints |
| `pnpm build` then `pnpm start` | Build and run the desktop app as it would ship |
| `pnpm build:web` | Static site in `apps/web/dist` |
| `pnpm test` | Core tests (Vitest) |
| `pnpm typecheck` | TypeScript across all packages |
| `pnpm opencalque <command>` | The CLI (`new`, `validate`, `describe`, `check`, `quantities`, `apply`, `svg`, `png`, `pdf`, `dxf`, `import`, `schema`, `guide`, `mcp`) |
| `pnpm schema` | Regenerate `schema/*.json` (documents, operations, extensions written as data) from the Zod schemas |
| `pnpm smoke` | Scripted interaction test of the built app (see §7) |
| `pnpm e2e` | Builds the web app, then drives it in Chromium with Playwright (`e2e/`, `playwright.config.ts`); asserts what it checks |
| `pnpm dist` | Build, then package the installer for this system into `apps/desktop/dist` |
| `pnpm notices` | Rewrite `THIRD-PARTY-NOTICES.txt` from what the web build holds (`--check` only compares; CI runs it) |

**Continuous integration (`.github/workflows/ci.yml`).** Every push to `main` and every pull request runs `pnpm typecheck`, `pnpm test`, `pnpm build:web` and the browser tests (`playwright test` against that build). A push to `main` that passes is then published as the web editor at https://opencalque.com, on Cloudflare, as static files with no server code (`wrangler.jsonc`; `apps/web/public/_headers` sets how long the files are kept by browsers). The workflow needs two repository secrets, `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. Installers are a separate workflow, started by a version tag (`release.yml`); it publishes only when every system built, and a tag with a hyphen (`v1.0.0-rc.1`) as a pre-release.

**Gotcha:** terminals spawned by VS Code extensions (including AI agents) have `ELECTRON_RUN_AS_NODE=1`, which makes Electron run as plain Node and crash on `app.whenReady`. Unset it for that command: `env -u ELECTRON_RUN_AS_NODE pnpm dev` in bash, or `Remove-Item Env:ELECTRON_RUN_AS_NODE` in PowerShell. A normal terminal is not affected.

To open a file at launch: `pnpm build`, then from `apps/desktop` run `pnpm exec electron . ../../examples/studio.opencalque`.

## 4. The document model

### Shape

A document is `{ format, version, id, name, unit: "mm", layers, nodes }`. `layers` and `nodes` are flat maps keyed by id. Beside them, optional maps of what the nodes refer to by id: `colors`, `dimensionStyles`, `materials`, `assets`. (Wall types, `wallTypes`, were one until format 2.) `info` says what the drawing says about itself (project, client, address, author) and `settings` how it writes its numbers (see Units).

Every node has `id`, `type`, `parent`, `order`, and optionally `name`, `layer`, `visible`, `locked`, `style`, `meta`. Types:

| Type | Own properties | Notes |
| --- | --- | --- |
| `page`, `component` | (`description` on component) | The roots. `parent` is `null`. |
| `group` | `opacity` | Holds other nodes; no geometry. See Groups below. |
| `line` | `a`, `b` | |
| `polyline` | `points`, `closed` | Drawn with the line tool: what it makes depends on how the drawing ends (see below). A closed one is called a polygon. |
| `rect` | `x`, `y`, `width`, `height`, `rotation` | Rotates around its top-left corner. |
| `ellipse` | `cx`, `cy`, `rx`, `ry` | |
| `text` | `x`, `y`, `text`, `size`, `rotation` | Single line, anchored at baseline left. |
| `wall` | `a`, `b`, `thickness`, `justify`, `bulge` | Its line (its middle, or with `justify` one of its faces), straight or an arc; drawn as a filled band, mitred into the walls it meets and cut by openings. |
| `dimension` | `a`, `b`, `offset`, markers, `extension`, text settings | An annotation. `style` is the dimension line; see Dimensions below. |
| `image` | `asset`, `x`, `y`, `width`, `height`, `rotation`, `opacity` | A picture, drawn where it is stacked (one under every floor stays under the floors). Its width and height in mm are its scale. |
| `instance` | `component`, `x`, `y`, `rotation`, `flipX` | Draws the component's children. |
| `parametric` | `kind`, `props`, `x`, `y`, `rotation`, `flipX` | Drawn by an extension. |
| `room` | `x`, `y`, `size`, `showArea`, `material` | A point and a name; the floor is found from the walls around it (`rooms.ts`), of a material when it says one. |
| `table` | `x`, `y`, `schedule`, `title`, `columns`, `labels`, `size`, `source`, `totals`, `decimal`, `system`, `language` | A table of quantities, worked out from a page each time it is drawn (`tables.ts`). |
| `divider` | `a`, `b` | Splits an open space into rooms where there is no wall. |
| `paper` | `x`, `y`, `width`, `height`, `scale`, `plain`, `titleBlock` | A sheet laid over the drawing; holds nothing (§4, Papers). |
| `annotation` | `a`, `b`, `text`, markers, `shape`, `bend` | A note with a leader. |
| `gridline` | `a`, `b`, `label`, `bubbles`, `size`, `font` | An axis of the building's grid, with its label in a bubble. See Grid lines below. |

### Rules that are easy to break

- **Units are millimetres; Y grows downward** (screen convention, not the CAD Y-up convention). A DXF exporter will need to flip Y.
- **Rotation is in degrees, clockwise on screen.** A placement applies mirror, then rotation, then translation (`applyTransform`).
- **The tree is `parent` + `order`.** There are no child arrays anywhere. `order` is a fractional index from the `fractional-indexing` package. Compare with `<`, never `localeCompare`. Ties break on id. Siblings can share a key (two people adding at once, drawings that hold some), and no key fits between two that do: put nodes among siblings with `ordersAt` (`document.ts`), which goes past a tie on the side of the neighbour that matters, never with keys made between the two neighbours directly (dissociating, ungrouping and moving forward failed on such drawings).
- **The tree has any depth**: a page or component holds nodes, and a `group` holds nodes too, nested freely. Use `holdsChildren(node)` to ask whether something can be a parent, `rootOf(doc, id)` for the page or component a node ends up in, and `leavesOf(doc, rootId)` for everything drawn there with groups opened up. `isContainer` still means page or component only.
- **Pages and components share one order space** (both have `parent: null`). Harmless, since they are listed separately.
- **Stroke width and dash are in screen pixels** and do not scale with zoom. Text size is in millimetres and does scale.
- **Style resolution** (in `nodePrimitives`): the node's `style` wins, then what the kind specified, then the layer colour, then `DEFAULT_INK`.
- **Documents are immutable.** Never mutate one; `childrenOf` caches a tree index per `nodes` object in a WeakMap and would go stale.
- **A new document always has page `page_1` and layer `layer_1`**, so scripts can target a fresh file without reading it.

### Operations

`applyOps(doc, ops)` shallow-copies the two maps, applies each op, and returns the new document; if any op throws `OpError`, the input is untouched. The ops are `add_node`, `update_node`, `remove_node`, `add_layer`, `update_layer`, `remove_layer`, `set_document`.

- `add_node` fills in `id` and `order` (on top) when omitted.
- `update_node` is a shallow merge. `null` deletes a key (except `parent`). `id` and `type` cannot change. Moving or reordering a node is an `update_node` of `parent` or `order`.
- Every resulting node is re-validated by Zod and by `checkNode` (parent is a container, layer exists, component exists, no component contains itself).
- `remove_node` on a container removes its children; on a component it also removes every instance of it. The last page and the last layer cannot be removed.

`applyOps` trusts its TypeScript callers. For untrusted JSON (CLI, AI output, later the network), call `parseOps` first, and `unknownProperties(doc, ops)` to tell the writer which properties it gave mean nothing (the CLI and the assistant both do).

- **Order keys are checked**: `order` must be a key of the fractional-indexing package (`isOrderKey`). Anything else ("top", "1") would sort, but nothing could ever be placed next to it, so `add_node`, `update_node` and the layer ops refuse it with a message that says what to write instead.
- **Long lists cost in proportion to their length.** One call keeps, per parent, an order key at or above its children's (`Batch` in `ops.ts`), so adding twenty thousand nodes does not search the drawing twenty thousand times; consecutive `remove_node` ops are done in one pass (`removeNodes`), with the same errors as one at a time. Do not add per-op scans of `d.nodes` to `applyOp`: that is what made a large DXF import take 40 s. The same holds in the editor: the Structure panel (`Objects` in `LeftPanel.tsx`) is a virtual list. Its rows, what is in the container and under each opened group what it holds (`linesOf`), are laid out by their fixed height (`ROW_HEIGHT`, which must match `.row` in styles.css), and only those in sight, with a margin, are drawn in a box as tall as all of them; laying out twenty thousand rows took six seconds after the import and again after each change. Which groups are open is kept by the list, since rows come and go as it scrolls. The first selected row is scrolled to when none of the selection is in sight, so something picked on the drawing is found in the list; picked in the list, it is in sight, and a range picked with Shift does not jump back to its start. A dragged row can scroll out of sight and be unmounted, so its `dragend` never comes: rows accept only a drag that carries `ROW_DRAG`.
- **Properties the schema does not know are kept** (`parse` in `ops.ts` goes through `keepUnknown`), so a node from a newer version keeps them through edits.

### The file format and its versions (`read.ts`, `repair.ts`, `unknown.ts`)

From 1.0 a drawing written by one version must stay readable by later ones, and must not be damaged by an earlier one:

- `readDocument(json)` checks `format` and `version`, runs the `MIGRATIONS` from the file's version up to `FORMAT_VERSION`, refuses a node type it does not know with a message naming it, validates with Zod, puts back what Zod dropped (`keepUnknown`), then `repairDocument`. It returns the drawing and the list of repairs; `parseDocument` is the same without the list. The app reports repairs in a note (`readDrawing` in `actions/file.ts`); `opencalque validate` lists them and exits 1.
- A drawing whose `version` is above `FORMAT_VERSION` throws `NewerFormatError`, which the app shows translated. Never half-read such a drawing: autosave would write it back without what this version did not understand.
- **Adding an optional property** keeps the version: older versions keep it untouched (and ignore it).
- **Adding a node type, or changing what an existing property means**, bumps `FORMAT_VERSION`, with a step in `MIGRATIONS` (`migrations.ts`) that brings older drawings up. Write the old version number in drawings that do not use the new thing, if older apps should still open them (`serializeDocument` is where).
- A drawing of version 2 that still carries wall types (`wallTypes`, a wall's `wallType` or `overrides`), saved by a development build of 1.2, has them taken out as they are from version 1 (`carriesWallTypes`, `withoutWallTypes`), which `readDocument` reports as a repair: ops refuse them, so a copy of such a wall (a paste, a dissociated component) failed.
- `repairDocument` fixes what would make a drawing refuse to open or refuse every edit: ids that differ from their keys, a missing layer or page, order keys that are not keys (reassigned in the same order), nodes outside every page (a missing parent, a group loop: moved to the first page), references to a missing dimension style, material or layer (dropped). Only what cannot be drawn is removed: a picture without its file, an instance of a missing component, an instance that makes a component contain itself. It returns the input unchanged when nothing needed doing.
- The JSON Schema in `schema/` describes what this version knows (`additionalProperties: false`); the app keeps the rest without validating it.
- **Version 2** (1.2): what a component holds is on no layer, and an instance has no style. `toVersion2` takes both out so that the drawing looks as it did: an instance with a style is given a copy of its component, named after it with a number, whose contents carry the style (one copy per component and style; a component placed inside goes through the same); something inside a component is hidden or locked when its layer was, and takes its layer's colour as its own (`var(--layer)` included) unless every placement of the component is on that layer, or, for a parametric object, or a dimension whose dimension style gives a stroke, whose own colours a stroke would override, follows the placement (`STROKED`; walls and rooms take the colour as a stroke like lines do). Three things draw differently: a component placed inside another on a layer of its own colour takes the colour of the outer placement's layer (an instance can be given no colour), a hatch laid on an instance starts from the component's origin rather than the drawing's, and a styled placement inside another no longer has its white backing painted in the outer style (`migrations.test.ts`). Files are written as version 2, which 1.0 and 1.1 refuse with their "newer version" message. Version 2 also takes wall types out (`withoutWallTypes`, run before `toVersion2`, so that the outline a type gave a wall inside a component is the wall's own when the colour of its layer is given to it): each type that walls were of becomes a material of the same name, id (another where the drawing has a material of that id, never `default`), fill and pattern, which its walls are made of, so they look as they did, follow the material when it is changed and are counted under the type's name; each wall is given as its own the rest of what the type gave it, its thickness unless it kept its own, and its height and its outline where it had none. A wall that already names a material keeps it. The layers of a type, drawn as lines inside its walls, and the types no wall was of go (the lines are not drawn any more, and a line is drawn where a wall of a former type meets one of another material, as between any two materials: both changed the drawings of 1.0 tests that had them). Operations that still name wall types are refused, saying so (`NO_WALL_TYPES`). It brings materials, walls made of them and tables of quantities (the `table` node type) too: it is not released yet, so they need no version of their own and nothing to migrate.

There is deliberately **no inverse-op machinery**. Undo keeps previous document objects, which is cheap because unchanged nodes are shared.

### Rendering pipeline

```
Node ──kindOf(node).primitives──▶ Primitive[] ──nodePrimitives (styles)──▶ SceneItem
buildScene(doc, containerId, registry) ──▶ SceneItem[] ──paintOrder──▶ canvas (draw.ts) or SVG (svg.ts)
```

Primitives (`path`, `ellipse`, `text`) are the only thing renderers know. Hit-testing, marquee selection, bounds and default snap points are all computed from primitives, which is why a new node kind or parametric object needs no renderer changes.

### Papers (`papers.ts`)

A `paper` node is a sheet laid on the drawing, in the spirit of a frame: `x`, `y`, `width`, `height` in drawing millimetres and a `scale` (the N of 1:N, default 100), so an A3 lying at 1:100 is 42000 × 29700. It is the hook for printing to scale later (FEATURES #6).

- **It has no children.** What lies entirely inside its rectangle is on it, **by position**, exactly as openings belong to walls. `paperContents(scene, id)` answers the question. This keeps selection, scope and hit-testing unchanged (things on a paper are picked directly, with no "entering"), and keeps the tree flat for collaboration.
- The tie is honoured only where a sheet is reproduced: duplicate, copy and cut take the contents along (`withPaperContents(ids)`, in `actions/clipboard.ts`). Moving, nudging, aligning, turning or scaling a paper acts on the sheet alone, which is how to frame a drawing: a sheet that dragged the drawing with it got in the way. Deleting a paper removes the sheet only. Changing its scale or format in the panel keeps its middle where it is. Pulling a corner on the canvas changes the scale, not the sheet (`paperScaleTo` in `papers.ts`, from the `handle` gesture): the corner keeps to the diagonal, drawn as the `guide`, the scale is a round one (`roundPaperScale`). A selected paper shows its format and scale above it (`paperLabel` in the canvas, "A4 · 1:100") and never its size in the drawing, which read as a size to draw to; with Alt the corner goes anywhere and the sheet takes a size of its own, as before.
- It draws as one path flagged `backdrop` (`PrimStyle`): `paintOrder` puts backdrops beneath everything whatever their stacking order, and `distToPrimitive` ignores their fill, so a click inside a paper reaches what is drawn there, or starts a selection box. A paper is picked by its edge or by its name.
- The name above the corner is editor chrome (`Overlay.titles`, drawn in screen-size text and hit-tested by `titleAt` in the canvas), not part of the drawing or of exports. Once a scene has a backdrop the canvas paints the surroundings as a grey desk; the grid is drawn over the sheets.
- **Paper tool** (`F`). The first click sets a corner and, if needed, zooms out until an A3 fits half the view. While pulling, `paperFormats` offers A5 to A0 at `paperScale` (store), upright or lying according to where the pointer is, as `Overlay.ghosts`; within 14 px of a format's corner the paper takes it (`constrain`), Alt gives any size. The properties panel sets format, direction and scale.

### On every sheet (`templates.ts`, `sheetContent` in `kinds.ts`)

A drawing may hold **one** thing drawn on all its sheets: a title, a logo, a north arrow. It is a component that says the sheet it was drawn on (`sheet: { width, height }`, millimetres of real paper), found with `sheetContentOf(doc)`. Every paper draws it over itself, multiplied by its scale, unless the paper is `plain`. Nothing is chosen per paper and nothing is copied, so a paper made by the tool, by a DXF import or by the assistant has it without being told.

This is what remains of two wider attempts, kept out on purpose. Layers shown on every page (removed in 0.8.3; `shared` on a layer of an older file is dropped on load) were in drawing millimetres at one fixed spot and did not follow a paper or its scale. Templates chosen per paper, with files, formats and a copy of the title block, did the job but asked the user to manage a list for a need that is "put this on every sheet".

- It is drawn by the paper, as the title block is, so it has no place of its own in the drawing: it keeps its place on the sheet and its printed size when the paper is moved, rescaled or copied, and screen, SVG and PDF agree. A click on it picks the paper.
- **Sheets of other sizes.** Each child of the component is moved as one piece so as to keep its distance from the corner of the sheet its middle was nearest to: what was drawn bottom right on an A4 is bottom right on an A3. Nothing is stretched, so a frame drawn round the sheet does not follow; the title block's frame does that.
- **Fields** are filled in for the sheet being drawn (`KindContext.sheet`, from `paperSheet`): `{sheet}`, `{scale}` and `{format}`, and `{page}` for the page the paper lies on. Off a sheet those three stay as written, which is how they read while the component is edited. `{project}`, `{client}`, `{address}` and `{author}` read the document's `info` anywhere.
- The title block stays what it was, separate: a paper lays it out by itself. The two can be on a sheet together.
- **In the editor**: the paper's panel has "On every sheet" under the title block: a button that starts it (`sheetContentOps`, empty, the size of that paper) or opens it, and a box to show it on this paper. `editSheetContent` (`actions/view.ts`) goes inside it with the sheet filling the view, remembers the view and the selection, and a store subscription brings them back when the scope leaves it, by whatever way. While it is the scope, `buildScene` lays its sheet under it (`templateSheet`, a locked backdrop). The fields only a sheet fills in (`SHEET_FIELDS`) are offered for a text only there.
- Not there: more than one per drawing, and bringing one from another drawing other than by copy and paste of what it holds.

### Title block (`titleBlock` in `kinds.ts`)

A paper with `titleBlock` draws a border and a block built from entries (`TITLE_FIELDS`). `titleBlockValues` resolves what each reads: project, client, address and author from the document's `info` (set with `set_document`; the project falls back on the document name, and a paper may still override project and author for itself), the names of the paper and of its page, scale, format, and the paper's own date and number, with text fields filled in. An entry is drawn when it is not in the paper's `hide` list (`['page']` by default) and is not empty; the block's rows and height follow from what is left, and a text too long for its place is set smaller. The panel (`TitleBlockEntries`) writes drawing-wide entries to `info` and the others to the paper.

### Fills and patterns

A fill is a colour and, optionally, a pattern over it: `style.pattern` (`PatternSchema`: a kind, a spacing, an angle, and the colour, weight and opacity of its strokes; the weight is `strokeWidth` in screen pixels as in a style, `HATCH_WEIGHT` (0.6) when unset). `nodePrimitives` draws it as strokes inside each closed shape of the node, cut to the shape with `clip` (`patternStrokes` in `modifiers.ts`, the same strokes the hatch modifier lays), from the origin of the drawing so that neighbouring walls carry it without a break. `{ kind: 'None' }` says "no pattern" where one would otherwise come from the wall's type. The hatch modifier remains, for files that use it and to stack with other modifiers; a room's floor takes `style.pattern` like any other fill.

**In the editor every fill is edited in one window**, `FillChoice` (`FillChoice.tsx`): a field showing the fill (a swatch with the pattern's picture over its colour, and its name or colour), opening on three tabs, None, Solid colour and Hatch, each name on one line (`white-space: nowrap`: a longer one takes the room the shorter leave). The tab shown is the kind of fill, worked out from the two properties (a pattern: Hatch; `'none'`, or nothing where nothing means no fill: None; otherwise Solid colour), and choosing a tab changes the fill at once: Solid colour takes the pattern away and gives a colour (the last one picked) when there was none, Hatch gives back the pattern last shown or plain lines, None takes both away or writes `'none'`. The Solid page is what the colour window holds (`ColorPanel`, shared with `ColorChoice`), less its Reset where that would be no fill, which is the None tab (`noReset`); the Hatch page has a preview drawn with `patternStrokes`, the pattern's rows (`HatchRows`: kind, colour, opacity, weight, spacing, angle) and the background, which is `style.fill`. The window sets `fill` and `pattern` together (a `FillChange`, made a patch by `fillPatch` in `FieldRow.tsx`; the field type `'fill'`), so one choice is one undo step. A fill field says what nothing means for it (`fallback`: `'none'` for plain shapes, white for walls and objects and for shapes inside a component, which is how they are drawn where it is placed, so that None writes `'none'` there; the room's default for floors) and whether no fill may be chosen (`filled`: not for a wall, whose fill must be opaque, see Walls). The window is as tall as its tallest page from the start (`min-height` of `.fill-menu`), so changing tab neither moves it from under the pointer nor runs it off the screen. Fills of a picture or a texture would be more tabs; they need assets referred to from a style, which nothing yet counts as a use (`serializeDocument` drops unused assets, and copying brings only those of pictures).

**Windows opened from a field** (`useFloating` in `floating.ts`: the colour, fill and weight windows) are drawn at the top of the page, placed once against their field, and closed by a press elsewhere, a scroll, a resize or Escape. One may be opened from another (the colour of a pattern's strokes, from the fill window): a press in a window opened later is not "elsewhere" for those before it, and Escape closes only the last one opened and goes no further, so neither the window it came from nor the tool in use is let go. The press that closes a window from elsewhere must not reopen it when it ends on its field (`closing`); that is cleared after the click the press ends with, caught on its way down, since every field stops its clicks from going back up: caught on the way up, it never came, and a window closed by a click on the next field of the bar above the tools refused to open again for a second and a half.

### Shared colours (`colors.ts`)

A drawing may hold named colours in `colors` (id, name, value). Any colour property (a style's stroke or fill, a layer's colour, a dimension's text colour) refers to one by holding `var(--<id>)` in place of a colour. Nothing is copied, so `update_color` recolours everything that refers to it with one operation and without touching a node.

- References are followed in one place, `nodePrimitives`, after the kind has drawn and the style is resolved; renderers and exporters only ever see plain colours.
- `remove_color` replaces every reference with the colour it stood for, so nothing changes appearance; a reference to a colour that is not there draws in plain ink.
- Copying to another drawing brings the colours along (`transplantOps`, `copyNodes`); they keep their ids, so pasting twice adds them once.
- **`var(--layer)` (`LAYER_COLOR`) is the colour of the node's layer**, for a fill, a text or a pattern's strokes that should follow the layer as a stroke with no colour of its own does. It is written like a reference but is not a shared colour (`colorRefOf` returns null for it, and `add_color` refuses the id "layer"). The colour window offers it as "Colour of the layer", without the layer's name: the Layer field above it already says which layer that is. `resolveColor` takes the colour it stands for as a third argument; `nodePrimitives` passes the node's layer colour, else the `ink` of the component placement it is drawn in, else the default ink. Elsewhere it resolves to plain ink.
- The colour window (`ColorChoice`) offers the layer's colour when the object is on a layer (`layerChoice` in the properties panel): for a stroke that is no colour at all, for anything else `var(--layer)`. It also has an eyedropper, the browser's `EyeDropper` (Chromium, so the desktop app too; hidden where there is none). A layer with no colour of its own shows a crossed-out swatch.
- In the editor a colour field (`ColorChoice`, used by `FieldRow` in `panels/properties/FieldRow.tsx`) shows a linked colour by name, in the accent colour with a link icon, and its list separates "Shared colours" from "This object only". The list of shared colours, with how many things use each, is under the layers (`Colors` in `LeftPanel.tsx`); each is changed in the same colour window, with `plain` (no shared colours to link to, no reset).
- **A colour may be see-through**: it is then written with eight hex digits, the last two its opacity (`#rrggbbaa`), the only form the colour window writes besides six digits. `parseColor` (`pdf.ts`) reads the alpha; the canvas takes the colour as it is, the PDF sets the opacity per fill and stroke, and the SVG export writes `fill-opacity` / `stroke-opacity` apart (`colour` in `svg.ts`), since not every reader of SVG knows eight digits. The DXF export writes no colours, only layers. Swatches draw over a checkerboard (`swatch` in `ColorChoice.tsx`). **A group's `opacity`** (0 to 1) is applied the same way: the group's kind fades the stroke and fill of every primitive it draws (`fadeColor` in `colors.ts`, which writes eight digits) and a picture's own `opacity`, so no renderer knows of it and nested groups multiply. A shape with no fill keeps how much it was faded (`faded` on the primitive), for the white an object backs it with (see Objects are solid in §9). Each primitive is faded on its own, so where two things of a faded group overlap the overlap is darker, unlike a layer faded as a whole in an image editor. In the properties panel it is an `opacity` field (`OpacitySlider` in `ui.tsx`), as is a picture's: each position is written as it moves and `collapseHistory` makes a drag one step to undo.

### Annotations

An `annotation` is a note with a leader: `a` is the tip on what it is about, `b` where the text sits, plus `text`, the symbol at each end (`startMarker`, `endMarker`: the same set as dimensions) and `bend`, how much the leader curves as a fraction of its length. The curve is a quadratic drawn as a polyline (`annotationCurve` in `kinds.ts`); its third handle is the middle of the curve, and dragging it sets `bend`. The text runs away from the tip, so text primitives gained `align: 'right'`.

In the editor the tool shares the text button (`TEXT_TOOLS`, `Shift+T`). After its two clicks the node stays a preview while the note is typed in `TextEditor.tsx`, which now serves any node that has words; while typing, the canvas leaves out only that node's text, not the node. `annotationTemplate` in the store holds the look of the next ones, edited in the panel while the tool is active, as for dimensions.

### Grid lines

A `gridline` is a line `a`-`b` with a bubble (a circle of diameter `size`, 800 mm by default) past `a`, `b`, both or neither (`bubbles`), touching the line, its `label` upright in the middle at half its height (`gridlineBubbles`, `gridlinePrimitives` in `kinds.ts`). A label too wide for the circle stretches it level into a pill (`half`, the length of its straight sides either side of the middle), its width estimated from the number of characters, as text widths are elsewhere in the core; the pill stays level whichever way the line runs, so its middle is set off by `r + |out.x| × half` to keep it touching the line. Labels of one or two characters keep the circle. Its `style` is the line; the bubble and the label are `own` primitives that take the style's colour and weight but never its dash, as a dimension's markers do. Its line is a snap line, its bubbles are not. It is a node type rather than a parametric object because its tool numbers the lines it draws: `gridlineTemplate` in the store holds the look and the label of the next one, and `finishShape` moves the label on with `nextGridLabel` (A, B … Z, AA; 1, 2 … 10; "A1" then "A2") each time one is drawn. The template starts in dash and dot. A double-click on one types its label in place, in the bubble nearest the pointer (`editingText.bubble`): `TextEditor.tsx` writes `label` instead of `text`, on one line, and the canvas leaves out only that bubble's label while it is typed (`withoutTyped`). It came in with format 2, before 1.2 was released, so it needed no version of its own.

The tool is in `TEXT_TOOLS` (G), a two-point shape (`TWO_POINT`, `shape()` in `canvas/shapes.ts`) whose end is held to 45° steps by Shift and takes a typed length and angle, as a line does.

### Rooms (`rooms.ts`)

A `room` node is a point and a name; **its outline is not stored**. `roomAt(doc, parent, point)` finds the space the walls and dividers around the point enclose, every time the room is drawn, so a room follows its walls and can never go stale. This is the same idea as openings and papers: tied by position, not by reference.

- **The floor is the space the walls leave, as they are drawn.** `roomRegions` takes every wall's outline (`wallOutline`: mitred into the walls it meets, the same as on screen, without the gaps of its doors and windows, so that a door does not open a room) and every divider (a line; a wall thinner than 1 mm is one too), grows each by half of `GAP` (50 mm) so that what comes within 5 cm of touching touches, unites them (`clipper-lib`, Clipper 1 in JavaScript, Boost Software License; in hundredths of a millimetre), and takes each hole of the union, grown back by the same half, as a room: out to the faces of its walls, with what stands inside it (a free-standing column, the walls of a room inside it) cut out of it and of its area. So a room closes exactly when its walls touch on the drawing, its floor follows their faces whatever their thicknesses, the lines they are drawn by and the way they meet, and nothing depends on the order the walls were drawn in or which way round. A wall standing in a room, such as a stub that leads nowhere, takes its floor from the room's area. Results are cached per document. Rooms used to be found from the walls' lines as a planar graph, drawn in by each wall's reach, with rules for ends that nearly met (corners, Ts, steps between walls of different thicknesses); each rule held alone, and they met in ways that slanted floors, left rooms open, or depended on drawing order. Do not bring that back.
- **Tested against what must hold, not only examples.** `rooms-robust.test.ts` draws 200 plans at random (`test/support/plans.ts`: grids of rooms with walls of every thickness and line, either way round, in two pieces, moved aside, with ends drawn short) and checks that every room whose walls touch closes, has its point on its floor, keeps its floor out of the walls, and is the same whichever way round each wall and in whatever order; it also checks the plans in `test/fixtures/rooms`, kept from real drawings as numbers only (no names or addresses), each room with the area it must have. When a room comes out wrong, add its plan there. `pnpm rooms:gallery [count] [file]` draws them all on one HTML page, each by its seed.
- A `divider` (a to b) bounds rooms like a wall of no thickness, to split an open space.
- **Its perimeter** (`regionPerimeter`) is the length of its outline, along the faces of its walls, doors included and what stands inside it left out; a room shows it under its area with `showPerimeter`, and quantities give it per room (`RoomQuantity.perimeter`, measured round the outline as it is placed, so a stretched component lengthens it).
- The room draws its floor as a path flagged `backdrop: 'floor'` (painted over papers and the pictures stacked under every floor, under walls and everything else, and not clickable), then its name and area as text. It is picked by its name. With no closed space around it, only the name is drawn. Selected on its own (or with other rooms only), it has no box around it (`Overlay.boxless`), only its outline lit, so no grips, and a press or a right-click inside where that box would be is not on it (`roomsOnly` in `canvas/shapes.ts`): it has nothing of its own to scale or turn, only its name to move by dragging it.
- Its `style` is split between the two: `fill` and `pattern` are the floor's, `stroke` the colour of the name and area. The floor is flagged `over`, so that colour never outlines it. In the Properties panel the room has two sections to match, Label (where its name is written, its text size and text colour, said as the text's, whether the area shows) and Floor (colour and pattern); its name is in the Name row every object has.
- A floor pattern is `style.pattern`, as for any fill; the `hatch` modifier works too, on any closed shape, stacking with other modifiers. Pattern strokes are clipped to the shape, which is why clip outlines may be any simple polygon (`segmentsInside` cuts lines for DXF).
- In the editor: the room tool (`A`) previews a room wherever the pointer is inside closed walls and places it on click; the divider tool (`Shift+A`) shares its toolbar button.

A curved wall bounds rooms by its outline, which follows its curve in short straight stretches, so a room's area is that of a many-sided shape, within a few thousandths of the true one.

**Its area is written as the room says** (`roomArea` in `kinds.ts`): in m², or in ft² with `system: 'imperial'`, with the decimal mark of `decimal`, as a table of quantities carries its own (both optional, so a drawing of 1.2 reads the same). The core knows nothing of the user's unit: the editor gives a room placed by someone working in feet or inches `system: 'imperial'`, and one with a decimal comma `decimal: ','` (`writtenAs` in `units.ts`), and the Name section of its properties changes both, for several rooms at once. A room's panel shows its area in the unit of the preferences (`formatArea`).

Rooms are a few times slower to find than when they were traced along lines: about 90 ms for a plan of two thousand walls, once per change of the drawing.

### Modifiers (`modifiers.ts`)

A modifier changes how a node is drawn without changing the node. Any node may carry `modifiers`: a list of `{ type, enabled?, params?, frame? }`.

- **Where they run.** At the end of `nodePrimitives`, after the kind has drawn and styles are resolved: `applyModifiers` hands the primitives to each modifier in list order, each working on the result of the one before. Because groups and instances draw through `nodePrimitives` of what they hold, a modifier on one applies to everything inside, after the modifiers of the things inside.
- **Pure.** A `ModifierKind` is `apply(prims, params, frame) → prims`. It never sees the document, which keeps undo, collaboration and the assistant unaffected.
- **`frame`** is a `Transform` placing the modifier on the drawing; positions among its parameters are relative to it. That is what lets `moveOps`, `movePatch`, `cloneOps` and `transformOps` carry modifiers along without knowing any kind: they only move frames. Reshaping a node by its handles leaves its modifiers where they are, on purpose.
- **Unknown kinds are kept and skipped**, like unknown parametric kinds, so a drawing made with an extension survives being opened without it. The field is in the schema for the same reason: fields the schema does not declare are dropped on load.
- **Clipping is an attribute, not a cut.** Crop gives every primitive a `clip` outline (`PrimStyle.clip`, a list of convex outlines, all applying at once). The canvas and the SVG export clip to it; hit-testing and bounds honour it; the DXF export, which has no such thing, cuts lines with `clipSegment` and keeps or drops a text by where it starts. Fills are therefore never cut geometrically.
- **Kinds.** `crop` is built in (`BUILT_IN_MODIFIERS`); extensions add more with `registerModifier`, looked up through `modifierKind(registry, type)`. A kind may give an `outline` for the editor to show.
- **In the editor**: `addModifier` in `actions/edit.ts` (Object › Crop, right-click, or the list in the panel), the Modifiers section of the properties panel (order, on/off, remove, parameters), and on the canvas the outline of each modifier of the one selected object, with corners to drag for an upright crop (gesture `crop`).

Not there yet: baking a modifier into ordinary objects ("apply"), a crop that refers to another object as its outline (which is what would make a paper a viewport), and parameters that are not numbers in the panel. Walls are joined before their modifiers run.

### Transforming (`transform.ts`)

`transformOps(doc, nodes, { pivot, mirror, rotation, scale }, registry)` turns, mirrors and resizes any nodes in proportion about a point, each through its kind's `transform` (`NodeKind` in `kinds.ts`, which every type must have, so TypeScript refuses a new type without one); a top-to-bottom mirror is `mirror` plus a half turn. Each type keeps its meaning: a wall's thickness and a text's size scale, a parametric object has its `unit: 'length'` parameters scaled instead of being stretched, an instance gets `scale` and `flipX`, text and pictures go to their mirrored place but stay readable, a paper stays upright. This is what made `scale` on instances (and in `Transform`) and `rotation` on ellipses necessary.

In the editor, `transformSelection` and `nudgeSelection` (`actions/edit.ts`) are behind the commands (Shift+R, Shift+H, Shift+V, arrow keys), the Object menu and the toolbar's Rotate button: quarter turns and flips about the middle of the selection. Turning about a point the user clicks is the Rotate tool (gesture `turn`, worked out in `turnAim` in the canvas): a first click sets the pivot, a second a point of the line the turn starts from (`from`), and the selection then turns by the angle from that line to the pointer, shown with the angle reading's arc and label; a third click applies it, or the angle typed in the quick bar (`drawLocks.b`, counter-clockwise as when drawing). Flipping is not a tool: the two flips are listed with the rotate tool in its toolbar button (`ToolGroup`'s `actions`) and act at once. The properties panel has no transform section: it shows what objects are, not actions. Its Rotation field sets an angle, and turns each object to it about its own middle, the middle of the box it fills unturned (`turnToOps`), as the knob does, rather than about the point its position is measured from (a rectangle's corner, a component's insertion point). It has no mirror field: `flipX` could only say left to right, so a thing mirrored top to bottom read as mirrored and turned 180°. Stacking order, aligning and spacing evenly are in the toolbar's Arrange menu (`ARRANGE` in `Stage.tsx`), each from the number of objects it needs. What a thing is called is changed in the Structure panel (double-click its row); only a room and a paper, whose name is drawn, have a Name field. On the canvas the box around a selection carries grips (`boxGrips` in `draw.ts`, gestures `scale` and `rotate`): corners scale about the opposite corner in 5 % steps, the knob turns in whole degrees, Shift in steps of 15, Alt freely. The box around one object that turns but has no frame (a text, a picture, a compass: `TURNING` in the canvas) is the box it fills unturned, turned with it (`turnedBox` in `transform.ts`, whose middle `turnToOps` turns about): it keeps its shape as the object turns, its knob stays under the pointer, and the object turns about its own middle, as from the Rotation field, so that turning it again does not move it. The box around several things or a group, which have no turn of their own, turns with them while its knob is dragged (`box` in the `rotate` gesture) and is upright around them again once let go. A single object with handles of its own (line, wall, paper) shows those instead and is transformed with the tools or the keyboard. Scaling a selection is uniform only.

**A box is resized as a box** (`resize.ts`). A single rectangle or ellipse has no points of its own to drag; it gets a frame that turns with it (`resizeFrame`, `frameGrips`): four corners that move two sides, four middles of sides that move one, the opposite side or corner staying put (`resizePatch`), Shift keeping the proportions from a corner, and the knob above the middle of the top side to turn it about its middle. The canvas draws it in place of the selection box (`frame` in the overlay) and drags it with the gesture `resize`. A turned rectangle keeps its frame, which it did not have when its corners were points to drag. Several objects together are scaled in proportion by the corners of their box, since stretching a wall, a text or a component one way has no single meaning; they are stretched instead by a width or height typed in their properties (below).

**Stretching a selection** (`stretch.ts`). The Width and Height of a selection of several, and for walls their size from axis to axis (`wallAxesBounds`, the box the middles of the walls span, whatever their reference line), can be typed: `stretchOps` moves the far side (right or bottom) by the difference, the near side staying, as a CAD stretch window over that side would. What moves is the points within the thickness of the thickest wall selected of the far edge (a millimetre with no walls): the ends of walls, lines, dividers, dimensions, annotations and grid lines, the corners of polylines. So the outermost wall on that side moves whole, the walls running across get longer, and a partition standing against it in a T still reaches it; walls keep their thickness, which is why scaling was not the answer (#7). Walls outside the selection joined at a moved end follow it (`wallEndFollowOps`), doors and windows go with a wall moved whole and stay in one lengthened; anything else moves whole when its middle lies along the far side. The owner chose the far side over everything past the middle of the selection, which would have moved partitions on a whole plan.

### PDF export (`pdf.ts`)

`toPDF(doc, registry, paperIds?, { fonts })` writes one page per paper, at the paper's real size and scale: a page is the paper's width and height divided by its scale, in points, and everything on it goes through the same `paintOrder` steps the canvas and the SVG export use. The file is written from scratch (objects, cross-reference table) with no library, so the CLI has it too (`opencalque pdf`).

- Text whose every character the standard encoding has (Latin-1 and a few more) is set in Helvetica, Times or Courier, fonts every reader has, so nothing is embedded; `WIDTHS` gives Helvetica's character widths for centred and right-aligned text.
- Any other text (Chinese, Greek, Polish…) is set in the TrueType fonts passed as `fonts`, each character from the first that has it, the runs of one font after another in one `BT`/`ET`. Each font used becomes a Type0 font with Identity-H encoding, a ToUnicode map (so the text can be searched and copied) and a subset holding only the glyphs used: `truetype.ts` reads the font and writes that subset, glyphs renumbered in the order first used, composite glyphs with their parts. Bold is the regular font outlined in its own colour. Without fonts, those characters print as "?"; a character no font has prints as the font's empty box.
- The fonts are in `fonts/` at the root, with their licences and how they were made (`fonts/README.md`): Noto Sans (280 KB), Noto Sans SC (10 MB, Chinese and kana), Noto Sans JP (5.5 MB) and Noto Sans KR (5.7 MB, Hangul). `pdfFontNames` gives the order they are tried in, the same for the CLI and the editor: Noto Sans, then Noto Sans JP for a Japanese text and Noto Sans KR for a Korean one, then Noto Sans SC, since the three draw many of the same Chinese characters differently. A text is taken as Japanese when it has kana, as Korean when it has Hangul, or, in the editor, as the language of the interface. `pdfFontCharacters` says which characters need fonts, so a caller loads only what is needed: `apps/web/src/pdfFonts.ts` loads a font only when the ones before it fall short. They reach the web app as lazily imported chunks holding a data URL (`?inline`), because the desktop app loads from `file://`, where `fetch` does not work, and the CSP keeps `data:` out of `connect-src`. The export window starts loading them when it opens, and the browser's save picker, which needs a recent click, falls back to a download when loading took too long. The CLI reads them from disk.
- Fills with an alpha and pictures with an opacity use graphics states; clip outlines become clipping paths; JPEG pictures are embedded as they are (imported plans are always stored as JPEG). Other picture formats are left out.
- Line weights are screen pixels on the canvas; on paper one pixel is `WEIGHT` points. In the editor they are chosen as what they print at, among six pen sizes (`PENS` in `strokes.ts`, 0.13 to 0.7 mm), with `WeightChoice`: a field and a list that show each with a sample of its thickness (drawn five times its width in pixels, so the thin ones differ). A weight that is none of them (1 and 1.4 mm were offered before) is listed in its place where it is used.
- A paper's **title block** is part of what the paper draws (`titleBlock` in `kinds.ts`), so the screen, the SVG and the PDF agree. It is language-neutral: values only, no captions.

`apps/web/src/pdf.test.ts` opens the result with pdf.js, the reader the app uses for import, to check that it is a real PDF with the right page sizes and text.

### Groups (`groups.ts`)

A group is a node with no geometry. Its members keep their own coordinates, so grouping never changes what is drawn; it changes what is selected, moved and stacked together. Consequences worth knowing:

- **Moving a group moves its leaves.** `kindOf(group).move` returns nothing; use `moveOps(doc, node, d)`, which recurses. Anything that moves nodes must go through it.
- **The scene has one item per direct child of the container being shown**, so a group is one item whose primitives are all of its descendants'. Double-clicking a group sets `scope` to it, and its children become the items.
- **Walls and openings ignore group boundaries.** Joints and cuts are computed over `leavesOf` the page or component, so grouping two walls separately does not break their corner.
- `remove_node` removes everything inside, at any depth, and `checkNode` rejects a group placed inside itself.
- `cloneOps` copies a node with its contents; `transplantOps` (in `components.ts`) is the shared deep copy between documents, used by library import and by paste.
- `placeInOps(doc, ids, parent, target?)` puts nodes in a page, component or group, next to one of what it holds (before or after it) or on top of it all, from anywhere in the same page or component, keeping their coordinates and their order among themselves; a group that `parent` is inside of is left out. The Structure list uses it (`placeIn` in `actions/edit.ts`) for every drop: on the middle half of a group's row a row goes into the group, which opens; above or below any row, at any depth, it goes next to it in whatever holds that row, so rows are dragged into and out of groups as well as up and down. Afterwards the objects are selected if they are among what is being edited, else the group they went into (or the one holding it there).

### Clipboard (`clipboard.ts`)

`copyNodes` builds a small document holding the copies on its one page, plus the components, pictures and layer names they need. That document, as JSON text, is what goes on the system clipboard, which is why paste works across drawings and windows and why a copy can be pasted into a text file. `pasteNodes` imports its components (reusing ones pasted before) and transplants the nodes, on top of what is already there (`onTop` in `transplantOps`: the top-level copies drop the order keys they had in their drawing and are added bottom first, so they keep their order among themselves). The editor keeps its own last copy as well, because a browser may refuse to let a page read the clipboard. Paste reads the whole clipboard (`navigator.clipboard.read`, falling back to the text): when it holds no drawing of ours but a picture ("Copy image" in a browser, a screenshot), the picture is pasted as it is (`placePicture` in `floorplan.ts`), rather than the editor's last copy: where a paste lands, on top, on the layer in use, selected, a pixel of it on a pixel of the screen it came from, made smaller to fit most of the view. It is not a plan to trace, which a dropped picture is: no layer of its own, no fading, no change of view or tool. It is kept as JPEG like a plan, or as PNG when some of it is see-through (a logo), which the PDF export takes uncompressed.

Where a paste lands is `pasteOffset`, so that it lands where the person is looking: at the right-click point when pasted from the menu (`menuPoint`, which the menu clears once its command has read it, or when it closes); back where it was copied from when that place is in view, so a cut thing returns exactly to its place; otherwise in the middle of the view. Wherever that is, if it would lie exactly on the same things (the original of a copy, an earlier paste), it moves on by two grid steps until it does not; offsets are whole steps so what was on the grid stays on it. Paste in place (`Mod+Shift+V`) takes no offset at all.

A clipboard also says where its contents were seen (`withPlacement`, `meta.placement` in the clipboard document): the component placements, outermost first, through which the scope they were copied from is drawn on its page (`scopePlacement` in `actions/clipboard.ts`, from the store's `through`); none for a page; left out for a component opened from the library, which is seen nowhere in particular. Pasting takes them out through those placements and into the ones of where they are pasted (`relocateClip`, which moves and transforms with `transformOps` as an instance draws, and undoes it in reverse order), before `pasteOffset`: cut inside a component and pasted on the page, a thing lands where the component drew it. A cut removes what it copies at once, in the same turn as it computes the copy; only the system clipboard is waited for, so a key pressed meanwhile cannot change what is cut.

### Declarative extensions and the warehouse (`declarative.ts`, `packages/warehouse`, `catalog.ts`)

An extension in code can do anything, so it cannot be downloaded and run safely. A **declarative extension** is JSON: parametric objects whose shapes have coordinates written as expressions. `compileExpression` is a small recursive-descent parser with no access to anything but the names in scope (looked up with `Object.hasOwn`, so inherited names such as `constructor` are not reachable) and a fixed list of functions. `declarativeExtension` validates the JSON, compiles every expression, and builds each object once with its defaults so that a misspelt name is refused at install time rather than when someone places the object. A cap on shapes per object stops a mistaken repeat count from freezing the app. A `path` may have a `radius`, an expression too, which rounds its corners with `roundCorners` (`geometry.ts`): a closed one stays one shape, filled and backed with white as a whole, as a cushion or a chair's seat must be, where an `arc` is only an open line.

The registry is one object that is refilled, not replaced: `loadExtensions()` in `extensions.ts` clears it and puts back the built-in extension (unless switched off) and every installed one, then bumps the version in `useExtensions`, which the canvas, the panels and the language setup depend on. It runs once at start, from `main.tsx`, not when a module is imported. Installed extensions are stored whole in the preferences. So that one of those that ship with the app gets what is added to it later, `loadExtensions` replaces an installed copy by the bundled one (`bundledExtensions` in `packages/warehouse`) when the bundled one has a later `version`: a change to a bundled extension's objects bumps its version.

What ships is in its own package, `packages/warehouse`: the libraries in `components/`, the declarative extensions in `extensions/`, and `standardRegistry()`, the built-in extension and every bundled one, which is what the CLI draws with (a drawing using the adjustable furniture comes out of `opencalque svg` and `pdf` as in the editor; before, those objects were placeholders) and what a server would use. The editor installs a bundled extension only when asked, so it builds its own registry. The libraries reach the editor through Vite (`import.meta.glob` in `catalog.ts`, by a path into the package since a glob takes no package name), not fetched by URL, because the desktop app is loaded from disk where `fetch` of a local file is not allowed. Libraries are separate chunks loaded when opened. A web catalog is fetched normally and needs CORS on its host. Library documents have fixed ids (`warehouse.furniture`), which is what lets a component imported twice be recognised. It is reused only while it still draws what the library holds: the library and "From a file…" import with `original` (`importComponents`), which copies the component, compares the copy with those already there from the same place, once both are in the same document (`sameComponent`: contents in order, whatever their ids, names, descriptions and `meta`), and keeps the copy only when none is the same. A component changed in the drawing, edited in place for instance, is so the drawing's own, and the library's comes in beside it; a nested component changed makes the one holding it come in anew too. Paste does not ask for `original`: a component copied and pasted back into its drawing is the same one, changed since or not.

### DXF import (`dxf-import.ts`)

`dxfOps(doc, parent, text, options)` reads an ASCII DXF into `add_layer`, `add_asset` and `add_node` operations. Y is flipped, `$INSUNITS` scales to millimetres, layers are matched by name (locked and hidden as in the file), and whatever is of a kind not read is counted in `skipped`.

- **What becomes what.** LINE, LWPOLYLINE and POLYLINE (a bulge is drawn as short straight stretches), CIRCLE and ARC (an ellipse, with `from`/`to` for an arc), ELLIPSE, SPLINE (a polyline through the points of the curve), SOLID, TEXT and MTEXT (formatting codes read for the font, bold and height, then dropped). An INSERT is a **group** of what its block holds, at any depth, named after the block; entities on layer 0 or coloured "by block" take the layer and colour of the placement. A HATCH is a fill: solid, or the nearest of our patterns (`patternOf`), and when its outline was drawn just before it (its source boundary object) the two are **one** closed shape, not a fill laid over an outline. A hatch filled with a picture, which the file lays as hundreds of tiles after it, takes the colour behind the picture or the picture's average colour, and the tiles are dropped. A rotated or aligned DIMENSION is a `dimension` (one measured along a direction has its second point brought onto that direction, so it reads the same), a MULTILEADER an `annotation` (`elbow`, straight, or a curve whose `bend` is worked out from the file's points). An IMAGE comes in when `options.picture(path)` gives the file, which the CLI does and the editor cannot.
- **Look.** Colour from the true colour or the colour number (7 and black say nothing: they are ink), transparency as the alpha of the colour (none at all hides the line), weight from hundredths of a millimetre to screen pixels at four to the millimetre, dashes from the LTYPE table.
- **Text height.** The height a DXF gives is that of a capital, ours the size of the font: `DXF_CAP` (0.72) converts, both ways, so the export writes it too.
- **Sheets.** A file whose paper space is laid out (something drawn on it, or several windows) comes in as that sheet rather than as its model: a `paper` at the origin, what is on the paper, and for each VIEWPORT what it shows of the model, moved and scaled to the window's place, left out when off its view, and wrapped in a group with a `crop` when it reaches beyond the window. Everything is multiplied by the N of the sheet's largest scaled window, so that what that window shows is at its true size and the paper is an ordinary paper at 1:N; `options.scale` gives N for a sheet with no scaled window (a page of legends beside plans). The result says `sheet: { name, scale }`. A window's frozen layers are honoured.
- **SketchUp LayOut** writes each thing seen through a window on a layer of its own, `LayerGroup_n`, declared right after the layer it was on in LayOut: `home` puts it back there. It writes hatch patterns of what a window shows in paper measures, so a pattern finer than a third of a millimetre on the sheet is taken that way. A page other than the one on show comes as a block of its name holding the VIEWPORTs, placed in the model; it is read as the sheet.
- Not read: attributes, arrays of inserts, non-uniform scaling of circles (drawn as polylines), angular and radial dimensions (drawn as the file drew them), a hatch's holes (each outline is filled), 3D.

Text written `\U+XXXX` is decoded; the export writes every character beyond ASCII that way (`dxfText` in `dxf.ts`), since a DXF of that age has no encoding of its own and would otherwise be read in the code page of the computer that opens it. The editor calls it from `placeDxf` (`actions/file.ts`), for the File menu and for a dropped `.dxf`.

### Arcs, curves, repeats

An arc is not a node type: an `ellipse` with `from` and/or `to` (degrees, clockwise on screen from the X axis) draws as an open path (`arcOf`, `ellipseArc`), so everything that works on an ellipse works on it; a mirror swaps its ends in `transformOps`. The Arc tool makes one from its two ends and a point it goes through (`arcThrough`, the `arc` gesture, which follows `draw` as `offset` does for a dimension): always a circular arc, with its angles unrounded so that its ends stay where they were clicked; three points in line make a line. A polyline with `smooth` draws a Catmull-Rom curve through its points (`smoothPoints`); the points stay the handles. The Curved line tool is the line tool (`poly`) making that polyline. The `array` modifier returns the primitives it is given plus translated copies; its steps go through the modifier's `frame`, so they turn and scale with the object.

### PNG in PDF (`png.ts`)

The PDF writer takes JPEGs as they are. A PNG is decoded by `decodePng`, which carries its own small `inflate` so that the core still needs nothing from a browser or from Node, and goes into the file as uncompressed RGB with transparency laid on white. Interlaced PNGs and other formats are left out. Text picks one of six standard fonts from the primitive's `font` and `bold` (`fontFor`); only Helvetica's widths are known, the others are estimated for centring. Text the standard fonts cannot print goes to the embedded fonts instead (see PDF export).

### PNG export (`exportPng` in `actions/file.ts`)

A picture of a page is its SVG export (`toSVG`), given a size in pixels and drawn by the browser onto a canvas, then saved as PNG: no rasterizer in the core, and the two exports look alike. It is in the editor rather than the core because it needs a browser to draw; the CLI exports SVG. The longer side is 2000, 4000 or 8000 pixels (`PNG_SIZES`), never more, as browsers refuse much larger canvases.

### DXF export (`dxf.ts`)

Entities only (LINE, CIRCLE, TEXT), R12-style, Y flipped to point up, layers named after the drawing's. Wall polygons share edges at joints; an edge that occurs in two polygons is left out, so two mitred walls export as one outline. Not handled: fills, line weights, pictures, and walls that merely overlap.

### Pictures and assets

A document may carry `assets`: a map of embedded files (`mime`, base64 `data`, pixel `width` and `height`). An `image` node refers to one by id. Keeping the bytes out of the node map means everything that only needs the drawing can skip them with `withoutAssets(doc)`, which is what the assistant and any AI workflow should read. `add_asset` adds one; there is no remove op, because undo must be able to bring a deleted picture back. Instead `serializeDocument` leaves out assets nothing refers to, so they disappear on save.

Images are a fourth primitive kind. `paintOrder` paints them where they are in the stacking order, as anything else: under the walls when stacked under every wall, over them otherwise. A picture stacked under every floor, as an imported plan is, is painted under the floors too, so rooms drawn over a plan to trace still colour it; one stacked over a room's floor goes over it. Until October 2026 every picture was painted beneath everything, whatever its place in the Structure list. They contribute no snap points. `assetUrl` caches the `data:` URL per asset object, because rebuilding a multi-megabyte string on every redraw is ruinous. The canvas decodes pictures asynchronously (`pictureFor` in `draw.ts`) and repaints when one is ready.

Plans are always stored as JPEG at 0.85 quality, scaled so the longest side is at most 4096 px. That keeps files manageable but means transparency is flattened to white.

### Dimensions

A dimension is drawn from four independently styled parts. The node's `style` is the dimension line. End markers (`startMarker`, `endMarker`: tick, arrow, open-arrow, dot, none) follow the line's colour and weight but are never dashed. Extension lines use `extension` and the text uses `textColor`, each falling back to the line when unset. Text also has `font`, `size`, `textPosition` (above, center, below), `textRotation` (aligned, horizontal), and the value format (`unit`, `decimals`, `showUnit`, or a `text` override).

Two primitive features exist to support this and are available to any kind: a primitive marked `own: true` is not overridden by the node's general `style` (the kind has already decided its look from the node's own properties), and `fill: 'stroke'` fills with whatever the stroke colour resolves to, which is how a filled arrow follows a layer colour.

**Text along a vertical line** (`verticalText`): text along the line is turned to read from below, which leaves a vertical line with two choices. `'down'` (the default, and what every drawing had before the setting existed) reads from top to bottom, `'up'` from bottom to top, as ISO 129 asks. A line within `VERTICAL_TEXT_TOLERANCE` (1°) of vertical counts as vertical, so that a line a hair off true, from a DXF or a rotation, does not read the other way from its neighbours.

### Dimension styles (`dimensions.ts`)

A dimension style (`doc.dimensionStyles`, ops `add_dimension_style` / `update_dimension_style` / `remove_dimension_style`) holds whichever look properties of a dimension it gives a value to (`DIMENSION_STYLE_PROPERTIES`: everything in `dimensionLook` in `schema.ts`, plus `style` for the line), **under the same names as on a dimension**, and only those. A dimension with `dimensionStyle` takes what the style defines; a value of its own wins by being there, part by part within `style` and `extension`. Nothing has to be resolved in the document: `styledDimension(doc, node)` is applied when drawing (the `dimension` kind, and `nodePrimitives` for the line's style), so a style can change without touching a node.

- Since a dimension's own value always wins, a style that defines a property differs from one that leaves it out only for dimensions that have none of their own. That is why putting a dimension in a style (`dimensionStylePatch`, used by the panel and the tool) takes away its own values for what the new style defines, and turns what its former style gave it into values of its own: it changes only where the new style says something, and taking a style off leaves it looking the same. `remove_dimension_style` does the same to every dimension of the style, as `remove_color` keeps what referred to a colour.
- `checkNode` refuses a dimension naming a style the drawing does not have. Copying brings the style along (`transplantOps`, keeping its id, as for colours), and the materials of walls and floors likewise.
- In the editor: the Dimension styles panel (`DimensionStylesPanel.tsx`) shows each style as a card, opened for the style of the dimension selected or of the dimension tool, with a tick per property (`Defines`) and the value set with the same rows as a dimension's properties (`FieldRow`, with the style posing as a dimension). The properties of a dimension, and the dimension tool, have a style choice; `TypedRow` marks what comes from the style. The tool's settings outlive the drawing, so `dimensionToolLook` (`actions/edit.ts`) drops a style the open drawing does not have, and a style that gives a unit is not overridden by the user's.
- A style defines the plain font as `'sans-serif'`, since no font is how a dimension says it; `FieldRow` shows that as the plain font.

### Walls (`walls/`)

A wall draws as one polygon per solid stretch (`wallPolygons`). Two mechanisms combine:

- **Joints where wall ends meet** are real geometry. A mitre is kept only while its point stays within `MITER_LIMIT` (2) half-thicknesses of the joint, that is for walls meeting at 60° or more; sharper corners are chamfered. All walls ending within 0.5 mm of a point form a joint. They are sorted by angle; each wall's face is intersected with the facing face of its neighbour on either side (`meet`), and the wall's outline runs corner → joint point → corner (`cap`). Because every outline passes through the joint point, any number of walls at any angles tile the joint exactly, including different thicknesses. A mitre that would spike out more than 4 half-thicknesses is cut off, and a wall too short to reach the inner corner falls back to a square end.
- **Walls are painted as one mass.** Wall paths carry `union: 'wall:<material>'` (the default material's walls `wall:`). `paintOrder` paints all their fills together, in the stacking order, grown by a 0.8 px seam in their own colour to hide the antialiasing hairline between touching fills, with the patterns laid on them (strokes marked `merged`): a pattern waits past the fills of its own material that follow it, so that walls of one material run on into each other with no seam across their hatch, and is painted before the next fill of another material, which covers it where that wall lies over it. Then comes the outline of the whole as plain lines, centred on the faces like every other line (`mergedOutlines` in `merge.ts`): each edge of a wall, or each run of its outline when its edges have looks of their own, cut where other walls cross it or have a corner on it, with the stretches that have wall on either side left out (an edge two walls share, a wall end against another's side, anything inside another wall), and what follows on joined into one line. Only walls of its own material, and walls stacked over it, hide a wall's edge (`unionMass` gives each shape its key and rank): a wall over one of another material shows its outline across it, as the Structure panel stacks them, and the one under is hidden there; an edge running along the face of a wall of another material under it is hidden all the same, within `MEET` and `MEET_SKEW`, since `materialSeams` draws the line there. Shapes are found through a grid of cells (`massOf`), and the last outline is kept while the same shapes are painted again, so panning costs nothing (2 000 walls take about 40 ms when they change). The DXF export writes the same stretches (`outsideMass`). Until 1.2 the outline was a trick (outlines at double width, then the fills over them), which drew every wall line half its width outside the wall: something set against a wall, or a line along its face, showed half a line off it. The walls are painted as one band, so they cannot be interleaved with other things; the band goes where the first wall primitive is in the stacking order: what is stacked under every wall (a plot boundary, a traced DXF) is painted under them, everything else over them. That includes the paper-white backing a placed component gives each closed shape with no fill.

Consequences: walls always paint beneath everything else, and wall fill must be opaque (it is white by default, `WALL_FILL`; a see-through wall would show the outlines hidden inside joints).

**A wall that stops against the side of another** (its end in that wall's body or on its face, with no other wall ending there: a T) is cut along the face it comes up to (`stopAgainst` in `cap`): the cut is where its two sides meet that face, a straight line for a straight wall, so at any angle it lies flat against it, with nothing in the other wall and no gap beside it, wherever its line ends in the other wall, on its face or its middle. It is left square, overlapping as before, when the end is in more than one wall (at a corner the cut would not be one line, and a cut along one wall's face could open a gap under the other), when it runs nearly along the other (`STOP_LIMIT`), or when the cut would reach beyond the other wall's ends. It is left whole too when the other wall is of another material and stacked under it, as the Structure panel orders them (`rank` of the wall index; a wall being drawn, not yet in the drawing, goes on top): it then lies over the other, drawn over it with its pattern and outline (`paintOrder`, `outsideMass`), so that what shows follows the order the user sees, by the owner's choice. A new wall of another material drawn into an existing one therefore overlaps it until it is sent under it (`[`); nothing reorders it by itself. Such an end, like the stopping end of a butt joint, is reported by `cap` (`Stop`: the wall and which of its faces).

### Curved walls

A curved wall is a wall with a `bulge`: how far, in mm, the middle of its line stands off the straight line from `a` to `b` (positive to the right of that direction on screen). The wall follows the arc of the circle through `a`, that point and `b` (`wallArc`); the bulge is taken as at most half the distance between the ends, a half circle. **There is no other node type and no stored centre or radius**: the two ends remain the whole of what ties a wall to its neighbours, so corners, `moveCornerOps`, `wallFollowOps` and everything else that works on wall ends needed no change, and a wall whose end is dragged keeps its bulge and simply follows a new circle.

- Inside `walls/`, everything worked out along a wall goes through a `Course` (`courseOf`, in `course.ts`): a length, the point and the direction at a distance along, the point a given distance to one side, and the projection of a point onto it. A straight wall and an arc each give one, so the outline, the gaps for openings, `overlap`, `snapOpeningToWall` and `splitWallOps` are written once. New code that walks along a wall should use it and never `wall.b - wall.a`.
- At a joint, a curved wall is mitred along the direction it is heading there (its tangent), which is exact at the joint itself. Its two faces are then points of the arc every 3° (`ARC_STEP`), starting where the mitre left off.
- For other modules: `wallLength`, `wallMiddle`, `wallPoints` (the wall's line as points), `wallParallel` (a line beside it, for the faces), `wallSides`, `wallSpot`, `wallContains`, `distToWall`, `bulgeThrough`.
- A door or window is straight: in a curved wall it sits as a chord, its two ends on the middle of the thickness, and cuts the wall between the two radii through them.
- In the editor the wall kind has a third handle, at the middle of its line, which sets `bulge` (`bulgeThrough`; under 1 mm the wall is straight again and the property is removed), and the panel has a Curve field. `transformOps` scales the bulge and a mirror changes its sign.
- Not done for curved walls: drawing one directly with the wall tool, `extendWallOps` / `trimWallOps` (a curved wall is left alone, though straight walls are extended to it and trimmed against it), and `dimensionChainOps` (no chain is made). A wall cannot be more than a half circle; make two.

### Corners and joints

A corner is the point where wall ends meet. **It is not a node**: like everything else about walls it is known by position, so it cannot fall out of step with the walls. `wallEndsAt(doc, parent, point)` gives the ends there, `moveCornerOps` moves them together, and `splitWallOps` puts a corner in the middle of a wall by making it two.

How two walls are joined is written on the walls, in `joins: { a?, b? }`, one value per end: `round` or `bevel` on both ends of the corner, or `through` on the wall that runs past with `butt` on the one that stops. `cornerJoin` reads a corner's joint as one choice and `cornerJoinOps` writes it to every end. In `cap()` the choice only changes the outer side of the corner (`meet` returns an arc or a cut in place of the mitre point); a butt joint returns square ends, and `wallSeams` gives the line of the stopping wall's end, drawn as an ordinary path because walls are painted as one mass. Where three or more walls meet they are always mitred. Rooms are unaffected: they are found from centerlines.


**An end can be set loose** (`joins` `'free'`, `looseEndOps`): it is then joined to nothing, even where other walls end at the same point, and `joinedNear` leaves it out, so everything that goes through it (`cap`, `wallEndsAt`, moving corners, the joint pickers) treats it as free; it ends square, or cut along the side of a wall it stops against. Joints stay inferred from position, which keeps walls independent of one another (components, pasting, editing together, the operations); `free` is where the inference is wrong, said by whoever draws instead of guessed by one more rule. Nothing refers to another wall, so nothing can dangle. `wallEndState(doc, wall, end)` says what an end is: the walls `joined` to it, those it `touches` without being joined (set loose, or a lining stopping against a wall), whether it is `loose`, and the end of another wall it `near`ly meets, within `NEAR_JOIN` (10 mm). The canvas shows it on the selected walls (`wallLinks` in `CanvasView`, drawn by `drawScene`, for up to `MAX_LINKED_WALLS`): a filled dot where joined, the walls joined there outlined faintly, a struck-through dot where touching without being joined, an orange dot tied to the end it nearly meets. The wall's properties say the same under At its start and At its end, with Detach, Join again, and Join them (`moveCornerOps` onto the other end, which writes the same coordinates to both). What follows a move is what is joined and nothing else: `wallFollowOps` (a wall moved whole) and `wallEndFollowOps` (one of its ends dragged) take the walls of `wallEndsOf`, so an end set loose, or a lining stopping against a wall, is left where it is, as the canvas shows. On the canvas, a press on an end of the one selected wall that other walls share without being joined to it is a drag of that wall's handle, not of their corner (`looseEndAt` in `picking.ts`, before `cornerAt`): the selected wall is the one that moves.

In the editor the selected corner is `corner` in the store (a point, never set together with `selection`). A press on a wall end selects it and a drag moves it (gesture `corner`; with Alt and a wall selected, only that wall's end); a wall is split from its right-click menu or the Object menu, never by a double-click, which only goes inside a component, a group or a text; the two halves meet in a butt joint, drawn as a line across; `CornerPanel` in `panels/properties/walls.tsx` shows its position and joint.

A wall that ends against the middle of another is cut along its face (see Walls); the merged painting of walls hides the line between them.

### Heights and quantities (`quantities.ts`, `chains.ts`)

There were wall types until format 2: a way of building walls, shared by the walls of the type, which took what it defined and could differ. The owner found them of no use: a plan is drawn once, and walls are made alike by selecting them and setting them together. They are migrated away, each into a material of its name (see the file format).

Heights are data for measuring, never drawn: a wall's own `height`, else `wallHeight` on its page (asked in the export window), and a `height` parameter on doors and windows. `quantities(doc, pageId, registry)` returns rooms, walls (each with its material), openings, floors, the walls by material and thickness, and the objects placed; what needs a height is `null` without one. `quantitiesCsv` writes them as tables; the editor passes translated labels and the separator its language expects. `wallOpenings` (`walls/openings.ts`) gives the doors and windows in a wall with their stretch of its middle line; `dimensionChainOps` uses it to make a group of ordinary dimensions along a wall. Those dimensions do not follow the wall afterwards.

### Materials and walls of materials

A **material** (`doc.materials`, ops `add_material` / `update_material` / `remove_material`) is a name and the `fill` and `pattern` it is drawn with. It belongs to the drawing, as a shared colour does: a wall (`material`) and a room (`material`, its floor) refer to it by id, and nothing is copied, so changing it changes all of them. `remove_material` leaves a room as it looked, the material's colour and pattern going into its own `style`, and makes a wall of it of the default material. **The default material** (`DEFAULT_MATERIAL`, the id `default`) is what walls are made of until given another: a wall of no material takes its fill and pattern under its own style. It is never referred to, cannot be removed, and need not be there: until its look is changed (the first card of the Materials panel, which adds it), walls are white as they always were, so drawings made before draw the same. `checkNode` in `ops.ts` refuses a reference to a material the drawing does not have; `repairDocument` drops one; copying brings materials along (`transplantOps`, keeping their ids, as for colours).

**A wall is of one material.** It is drawn in that material's fill and pattern, under the wall's own `style` (`nodePrimitives`, as a room's floor takes its material's); an insulation's zigzag is laid along a straight wall from one face to the other (`wallFrame`), other patterns from the drawing's origin, so that walls of one material run on into each other. **A wall of several materials is several walls side by side**, each of one material and its own thickness, drawn by the face they share (`justify`) so that they stay flush. This was chosen over layers inside a wall: those were built for 1.2 (a wall carrying a list of layers, joined layer by layer at every corner, T and crossing by priorities of materials) and taken out before release, because every kind of junction needed a rule and every rule had edge cases the owner kept meeting; with walls side by side the plan shows what was drawn, and the junctions are those of plain walls, which hold. What that leaves to the user (drawing a lining, moving it with its wall) is the price.

**What is drawn.** Walls are merged shapes (`union: 'wall:<material>'` on their primitives), painted together whatever they are made of: their fills, then the outline of the whole, which leaves out wherever two walls share an edge (`paintOrder`, `mergedOutlines`), so the outline round walls of every material is one. Where walls of two materials overlap (one crossing the other), the one stacked over shows its pattern and outline over the other. Where one material meets another, the line is drawn again over them (`materialSeams` in `walls/seams.ts`, a plain path of the wall's look): the stretches of a wall's outline that lie along the outline of an earlier wall of another material, run the other way round, so the two lie on either side, within `TOUCH` (5 mm) and `SKEW` (about 1°), since a plan traced by hand is that much out here and there and the union hides a line wherever two walls touch or overlap; the later wall in the drawing's order draws it, on its own face, centred as the outline is, so that one runs on into the other. Painting each material apart (tried first) left a hairline of the later fill over the earlier one where they met. Walls of the default material count as one material, and a drawing with no materials draws no seams and paints exactly as before. A wall has no fill of its own to set any more: its look is its material's, and choosing a material takes off a fill a wall was given before.

**A wall laid against another is not part of a corner they share** (`joinedNear` in `walls/spatial.ts`, behind `wallEndsAt` and `cap`): a lining drawn from the inner corner of a room along its wall has its end at that corner, where it would otherwise be mitred with the two walls of the corner, and the corner and the lines across the ends of its walls would come out wrong. Of walls with an end at a point that leave it the same way face to face (`laidAgainst` in `course.ts`), the thicker is joined there and the others' ends are free, ending square against the other wall of the corner. The same goes for a lining drawn into the T a wall makes with the wall it lines (`abuts`): the lining's end lies flat against that wall's side, from the other side of its face, both lines ending where the faces meet; it is a lining when a third wall it is laid against runs past the point. It is not joined there, and stops against the side. Two walls making the same L with no wall lined are a corner and stay joined: the plan cannot tell them apart otherwise, and corners drawn so (an L of a wall's inner face and another's outer face) are common. `wallEndsOf(doc, wall, end)` gives a wall the ends at one of its own: the corner's, or itself alone.

**Doors and windows go through walls laid against their wall** (`openingIndex` in `walls/openings.ts`): an opening is in the wall whose faces hold the stretch it cuts, as before, and from there it cuts every straight wall running the same way with a face on a face of a wall it cuts (`laidAgainst`, within `FACE_TOUCH`), over the same stretch along it (`along`), wall after wall (at most `MAX_STACK`), looked for within `STACK_REACH` of the opening. So a door set in a brick wall goes through its insulation lining and the plaster on that. The opening's own drawing (its frame) is as deep as its own wall.

**Quantities** count each wall under its material: `WallQuantity.material`, and `materials` the walls of each material and thickness (length, net face, volume); the table of walls (`walls` schedule) lists them by material and thickness, with how many. 

**In the editor**: the Materials panel (`MaterialsPanel.tsx`) lists them as cards (name, fill in the fill window) after the default one, with "Add common materials" (`COMMON` in `materials.ts`, a dozen, named in the user's language when added); a material in use is deleted after a question. A wall's properties have a Material choice (`WallMaterial` in `panels/properties/walls.tsx`): the default, the drawing's, the common ones (added to the drawing in the same step) or a new one, for several walls at once too; its fill field shows what the material gives it. A room's floor has a Material field (`roomFields` in `fields.ts`); a floor of a material, like a wall, has no fill field (its look is its material's, and choosing one takes off a fill it had, `unfilledPatch` in `materials.ts`), unless a file or a script gave it one, shown as overriding the material, to be reset. The eyedropper gives a wall or a room the material of a wall or room it is taken from, and a fill only where no material gives one (`lookFrom` in `actions/edit.ts`). The wall tool draws walls of the material chosen beforehand (`wallMaterial` in the store, `WallToolMaterial` in its quick bar and its properties), of the default one in a drawing that does not have it, since tool settings outlive drawings.

### The line of a wall (`justify`), extending and trimming

**A wall is stored by its line, which is its middle or one of its faces.** `a` and `b` are the line; `justify` says which: absent (or `'center'`), the middle; `'left'` or `'right'`, that face as the wall runs from `a` to `b`, the whole thickness lying on the other side. Corners are where lines meet, so walls drawn by their inner face share their inner corners and keep that face flush whatever their thicknesses, the step showing outside; and any change of thickness (a layer, dragging the other face) grows away from the line, moving nothing else. This is Revit's location line and ArchiCAD's reference line. Without it a corner had to be on the middle line, so two walls of different thicknesses joined end to end were always centred on each other.

`wallSides(wall)` gives how far the wall reaches to its left and to its right of its line, and **nothing that draws or measures a wall assumes them equal**: faces are at `-left` and `right` across the line (`Course.offset`, `Course.project`'s signed `across`, `wallSpot`). At a joint each `Ray` carries `plus` and `minus` (its reach towards `perp(d)` and away, from `reachAt`: leaving from `a` the plus side is the wall's right, from `b` its left), which `meet` and `cap` use for the faces; the mitre limit is measured against the faces that meet, so a right-angled outer corner a whole thickness from the joint stays sharp. Doors and windows go in the middle of the thickness (`snapOpeningToWall`), and are in a wall when within its faces (`overlap`, `wallContains`). Rooms inset each side by the wall's reach on the room's side. A mirror swaps `justify` (and `edges.left` / `edges.right`), so the same face stays the line. The wall tool stores what its quick bar says (`wallJustify` in the store): the points clicked are the corners. In the Properties panel the Reference line choice (`WallLine` in `panels/properties/walls.tsx`, the same `JustifyPicker` as the quick bar) uses `wallJustifyOps`, which leaves the wall where it is, with its doors and windows: its line goes onto the line chosen, and its corners with it, through `lineAcrossOps` (what making a wall thicker from one face uses), the walls joined there sliding along their own line to stay joined, those carrying straight on from it left where they are, those that stop against its sides untouched. A thickness given afterwards then grows away from that line. Several walls are changed one after the other, each from the drawing the one before left, so that a corner two of them share goes where both new lines meet. (Until 1.2 the line stayed and the wall moved across it; the owner found it got in the way of changing thicknesses afterwards.) Pointing at a face there rings it on the drawing (`edgeHover`), as left and right depend on the way the wall was drawn.

`extendWallOps` and `trimWallOps` (`walls/edit.ts`) work on free ends only (ends no other wall ends at), against the lines of the other walls.

**Flipping a wall** (`flipWallOps`): a wall drawn by a face is turned over its line, as Revit flips one: `justify` goes to the other face, so the wall lies on the other side of its line, its corners where they are and the walls joined there mitred to it anew, its doors and windows moved across with it (`openingsAcross`). The look given to the face on the line stays with that face (`edges.left` and `edges.right` swap). A wall drawn by its middle has nothing to flip. In the editor it is `edit.flipSide` (`flipSide` in `actions/walls.ts`), `Shift+Space` by default: while drawing walls it turns the wall tool's `wallJustify` from one face to the other, while placing a door it changes the hinge of what is placed, and with the select tool it flips the selected walls and changes the hinge of the selected doors (a window, with none, its `flip`).

**The trim tool** (`X`, sharing a toolbar button with Split, `CUT_TOOLS`) is CAD's quick trim: `trimPlace(doc, node, p)` (`split.ts`) finds where other things cross a straight wall, a line, a divider or an open polyline (for a wall, the lines of the other walls, so that what is left ends against them in a T; for a line, other lines, polylines, rectangles and the faces of walls), and the stretch between the crossings on either side of the pointer, or from an end to the nearest; the canvas shows it struck through (`Overlay.trim`) and `trimOps` takes it away: an end cut back, a stretch in the middle leaving two parts (`splitOps`, then the first cut back). A curved wall and what nothing crosses are left alone.

**Thicker from one face (`wallThicknessOps`).** Keeping one face where it is while the other moves means moving the line by however much of the change it takes: none for a wall drawn by the face that stays, half for one drawn by its middle, all of it for one drawn by the face that moves. `wallThicknessOps(doc, wall, thickness, side, registry)` does that and moves what is tied to the line by position: at each corner, the other walls slide along their own line when they make one (the corner goes where that line meets the moved line), and otherwise the corner moves across with the wall; where they carry straight on from it, they are left where they are and the two walls butt (turning them would be wrong whatever they are); an end of the wall that stops against the side of another slides along that other wall; walls that stop against its sides are lengthened or shortened along themselves (unlike `wallFollowOps`, this handles the T). Its doors and windows move with the middle of the thickness (`openingsAcross`), by half the change. A curved wall keeps its centre and changes the radius of its line, its new bulge worked out from its new chord. With `side` null both faces move and the middle of the thickness stays. Lines meeting the wall's line at less than `SLIDE_LIMIT` (sine 0.25, about 15°) would slide far, and are treated as carrying on from it.

On the canvas, a press on a long face of the one selected wall starts the `face` gesture (`faceAt` in `canvas/picking.ts`), offered only when the wall is at least `FACE_MIN` (8) pixels thick on screen, within a quarter of that thickness of the face (5 pixels at most), so that its middle is left to move it by. The pointer shows a resize cursor across the wall and the face is drawn over (`Overlay.face`). Dragging sets the thickness from where the pointer is across the wall, snapped to points and lines of other objects (not to what moves with the wall, found by trying the ops once at the start) and otherwise by `thicknessStep`, steps of at least 3 pixels (1 to 25 mm); Alt leaves out both, as it does everywhere. Ctrl (Cmd on a Mac) passes no side, so both faces move: Shift already means a constraint and Alt freedom from snapping, and Ctrl is how office programs resize from the middle. The store's `wallFace` tells the hints whether a face is pointed at or dragged.

The line across an end of the selected straight wall (`endAt`) starts the `end` gesture, checked before corners: the end goes along the wall, its direction kept and its other end where it is, to the projection of a snapped point or by lengths of `gridStep`, and the length is written along it. Within `END_POINT` (5) pixels of the point at the end, the press is the corner's, which moves the end anywhere as before. That end is a free one (no other wall ends there), or one joined to another wall where the line across is drawn (`endLineShown`), mostly the step between two walls in line of different thicknesses: the ends of the walls joined there (`wallEndsOf`, kept in the gesture as `joined`) go to the same point, so the step moves along and the walls stay joined. A mitred corner has no such line: its corner is moved, or the wall meeting it.

**Automatic, and firm choices.** An end with no `joins` value is automatic: `meet` brings the corner to a point, or cuts it off once the point would pass `MITER_LIMIT`. That is a rule of drawing, never written back to the walls: the angle of a corner changes in too many ways (dragging, typed coordinates, a neighbour that follows, scripts), and a joint rewritten on the way would not come back when the angle did. What is written is only what someone chose: `'miter'` keeps the point at any angle, `'bevel'` cuts at any angle. So that the panel never claims what is not drawn, it shows automatic as its own choice, pictured by what it comes to now (`autoJoinCuts`).

**The lines of a wall (`edges`).** How a corner is shaped (`joins`) and how its lines are drawn (`edges`) are separate. `edges.left`, `edges.right`, `edges.a`, `edges.b` are each a `WallEdge`: `show`, and a stroke, weight and dash of its own. With any of them set, the wall is filled whole with no outline of its own and its outline is drawn edge by edge as open `union` runs (`wallOutlineRuns`, tagged with their edge), each carrying the edge's look with `over: true` so that it wins over the wall's style and what it leaves unset falls back to it. Across an end, at a joint of two walls either wall can ask for the line (`show: true` wins) or against it; left unsaid it is drawn where one wall stops against the other and not where two are joined into one (`endLineShown`, `endLineOps`, which tells both walls). `splitWallOps` gives the two halves `show: true` at the cut. A line inside the mass of another wall stays hidden by that wall's fill; the DXF export drops what has wall on both sides of it.

**The butt joint at any angle (`cap` in `walls/joints.ts`).** The stopping wall's end is the stretch of the passing wall's near face between its own two sides, so it is cut obliquely whenever the walls are not square to each other; the passing wall ends square, just far enough past the joint to cover that stretch. When that would overrun the joint by more than 2.5 half-thicknesses (the walls bend by less than about 45° from a straight line, as two halves of a split wall do), both are mitred instead and the mitre line is kept as the seam, so they still read as two walls. A square cut at a fixed distance, as it was first written, is only right at 90°.

### Staying joined (`wallFollowOps`, `wallEndFollowOps`)

Walls are tied to each other only by having ends at the same point, so a move has to honour that explicitly. `wallFollowOps(doc, moved, d, registry)` returns what must follow a move for the plan to stay in one piece: the ends of other walls that met an end of a moved wall (those walls stretch and turn), and the doors and windows sitting in a moved wall. `wallEndFollowOps` does the same for one dragged corner. The canvas adds them to the `move` and `handle` previews unless Alt is held. Not handled: a wall ending against the middle of another (a T). Openings in a wall that was stretched or turned are put back in it after the edit, whatever made it (`openingFollowOps`, see Openings). Changing a wall's thickness from one face handles both (`wallThicknessOps`, above).

### Openings

A parametric kind becomes a wall opening by implementing `opening(props) → { from, to }`: the stretch of its local X axis that it cuts. There is no stored link between an opening and a wall. The association is **geometric and recomputed on every draw**: an opening cuts a sibling wall when both ends of its span lie between the wall's faces (`overlap`). The same test finds the host wall, whose thickness is passed to `build(props, env)` as `env.wallThickness`, so a door adapts to the wall it is on.

**Stretched by its ends (`size`).** A parametric kind may say which of its length parameters is its size along its own X axis from the insertion point (`size: { x: 'width' }` in code, `"size": { "x": "width" }` in a declarative extension); the door and the window do. The `parametric` kind then has two handles, the ends of that size on its axis (`handles(node, registry)`; `NodeKind.handles` and `moveHandle` take the registry for this), and a selected door or window shows them in place of the box that scales and turns it: `moveHandle` reads where the pointer is along the object's X axis (`inverseTransform`), sets the width from the end that stays, and for the start moves the insertion point too, never below 10 mm. Its width is written beside it, as a wall's length is. A scaling box multiplied every length of a door together (its width, its frame, its sill); stretching changes only the width. Objects that say no size (stairs, the compass) keep the box.

**Resized as a box (`box`).** A parametric kind may instead give `box`: `bounds(props)`, the box it fills in its own coordinates, and `resize(props, { width?, height? })`, the parameters that make it fill another, rounded to what it can be. `resizeFrame` and `resizePatch` (`resize.ts`, which take the registry for this) then give it the frame a rectangle has, eight grips and the knob, turning and mirroring with it: `parametricResize` reads the pointer in the object's own terms (`inverseTransform`; for a mirrored one, the frame's left is its right), asks the kind for the parameters, and places the object so that the side held stays where it was, or along a size that was not pulled but changed with the other, its middle. The stairs use it: up and down a straight stair gains or loses whole steps of its tread, across it is as wide as it is pulled (not below 300 mm); an L-shaped one lengthens its first flight up and down and its second across; a U-shaped one adds a step to both flights for each tread, and widens the gap between them across; a spiral stays round, its radius following. The washbasins (one bowl or two) are a counter as long and deep as it is pulled (not below 300 mm), whose bowls and taps keep their size, each bowl in the middle of its share of the counter and made smaller only when that share cannot hold it. The bathtub is as long and wide as it is pulled (not below 500 mm), its rim keeping its thickness and its drain its size and its distance from the end. Its sizes are written beside it while it is unturned, and the hints say it takes whole steps. A declarative extension says it as data, `"box": { "width": "<key>", "height": "<key>" }`, for an object filling the box from its insertion point to those two lengths, set in whole millimetres; the adjustable furniture (table, bed, shelving) does.

In the editor, `snapOpeningToWall` puts an opening on the nearest wall: centred under the cursor, rotated to the wall, facing the cursor's side, edges rounded to the grid along the wall. It is used when placing and when dragging a single opening (which then keeps the side it already faces). Alt disables it.

**Following the wall** (`openingFollowOps` in `walls/follow.ts`). With nothing stored, an edit that changes a wall and not its openings would leave them behind. So every edit in the editor (`applied` in `store.ts`, behind `apply` and `preview`) is followed by `openingFollowOps(before, after, changed)`: for each straight wall it changed, the openings that sat in it before (`hostWall`) and that the edit left alone are put back in it. One keeps its distance from the end that stayed; in a wall moved or turned whole, it moves or turns with it; in a wall both of whose ends moved, it keeps its place as a share of the length; it keeps its place across the thickness, turns with the wall, and is held within the wall when the wall can hold it. Left as the edit left them: what the edit moved itself (`wallFollowOps`, `openingsAcross`), what is in a curved wall, what is in another wall after the edit (the other half of a wall split in two), and what is in a wall whose middle runs where it ran (a wall turned round). The ops it adds are part of the step, so undo, the history and a sync layer see them. This was chosen over storing a host wall on each opening (a change of format, ids to remap in every copy, split and deletion): the tie stays positional, and no edit of a wall has to know of openings. Scripts and the CLI apply ops as given; they may call it themselves.

Consequences of the geometric link: an opening nudged out of the wall's thickness silently stops cutting, and an opening on a wall end inside a mitred joint can produce odd outlines.

### Clearances: temporary dimensions (`clearances.ts`)

As in Revit, the one thing selected shows how far it stands from the walls around it, and a distance typed moves it there. Nothing is stored: `clearances(doc, node, registry)` works them out from the drawing as it is, each a `from` on the thing selected, a `to` on what it faces and the `length` between (a clear distance, face to face):

- a straight wall: from the middle of each face, straight out, to the first wall met;
- a door or window in a wall (`hostWall`): from each side, along the wall, to the nearest face of a wall crossing or meeting it, cast along both faces of its wall and the nearer kept (so that at a corner it is the inside face, and a wall stopping against its wall, cut along that face, is met), or to the next opening in the same wall; walls running along its wall (its other half past a joint, a lining) are not measured to;
- anything else that has a box (a component, a parametric object, a rectangle, an ellipse, a group): from the middle of each side of its box, left, right, up and down.

Rays meet the drawn outlines of the walls (`wallPolygons`, mitred as on screen) within `REACH` (30 m), entering them only: a wall the ray starts inside is passed through. `clearanceOps` moves the thing along a clearance, with `moveOps` and `wallFollowOps`, so the walls joined to a wall follow it and its doors and windows go with it. Moved by the difference typed, it would meet the distance only if what it faces stayed put; a wall it faces may be joined to it (two sides of a triangle) and turn with the move, so the clearance is measured again where it went (the one running the same way, starting nearest to where it should) and the move corrected by secants until it is within `MET` (0.01 mm), `TRIES` times at most.

In the editor, `useClearances` (`canvas/clearances.ts`) gives them while one thing is selected with the select tool and nothing is dragged, drawn or typed, unless Show temporary dimensions (`showClearances`, in View and the view bar) is off, and `shownClearances` keeps those worth showing: an object other than a wall or an opening only to walls within `FAR` (2 m), since across a room the distance says nothing of where it stands, and each length where it covers neither the object's box, nor its size labels, nor another length (the middle of its line, then past the wall it reaches, then beside its line; one that fits nowhere is left out). The canvas draws them thin, grey and dashed, their length on a light ground, boxed only under the pointer (`Overlay.clearanceHover`, from the select tool's `hover`, which gives the pointer a hand there); a press on that box sets `measuring` in the store (`clearanceAt` in `picking.ts`, before any grip), and `ClearanceEditor` puts a field over it: Enter moves, Esc or leaving it closes. It is focused once the click has finished, since the browser moves focus to what was clicked after the press.

### Tables of quantities (`tables.ts`, `quantities.ts`)

A `table` node is a table drawn from what a page holds, worked out again each time it is drawn, as a room is from its walls, so it never goes stale. `schedule` says what it counts (`SCHEDULES`: the objects placed, floor areas by material, rooms, walls by material and thickness, doors and windows; an unknown one draws nothing, so a newer version may add some), `columns` which of the schedule's fields it shows (`SCHEDULE_FIELDS`, `SCHEDULE_COLUMNS` when it says none), `source` the page it counts (its own page or component otherwise), `only` the rows it shows, by the key each row has (`rowsOf`: a component, or a model of parametric object with its parameters; a material's id; a room's id; a material's id and a thickness; a kind and size of opening. Keys hold ids rather than names, so that renaming keeps a row chosen, and are worked out from the quantities in metres, so that a table set in feet keeps them; `tableItems` lists every row it could show, once each, for the panel to choose from, two rooms of one name told apart by their area), the others left out of it and of its total, and `rowsPerBlock` how many rows go one under the other before the next go into a block beside them, with the headings again, the total at the end of the last (`tableLayout`'s `blocks`), so that a long legend stays on its sheet. `quantities` gives the numbers, measured once per drawing and page however many tables count them (`measured`), and converted to feet with `quantitiesIn` for `system: 'imperial'`; it now also counts floors by material, walls by material and thickness over their net face, and the objects placed: each component, a component placed inside another once for each placement of that other (to the depth instances are drawn), and each kind of parametric object; hidden things are not counted. Rooms, walls, doors and windows are counted inside the components placed on the page too (`placedOn`), once for each placement, at the size they are drawn: each carries the linear part of how it is placed (turned, mirrored, scaled, stretched), which multiplies a floor's area by its determinant and a wall's length by how much its line is stretched, its thickness being what keeps the area of its footprint; so a building whose floors are components placed on a page is measured with that page. A total row adds up what can be: counts, lengths, areas, volumes, but not the faces of layers of different materials, which add up to nothing.

**Its words are its own.** The core is in no language, so a table carries the words it is written with: `labels` (the heading of each field, `total`, `none`, with `{unit}` where the unit of the drawing's system goes), `title` and `language` (the language of the names it takes from an extension, from the registry's translations). The editor writes them all when it makes a table (`newTable` in `actions/tables.ts`), in the language in use (its numbers following the drawing's settings), and they then stay as written, as the names of layers do, so the drawing reads the same wherever it is opened; the Properties panel changes them (`TableSettings`). What it leaves out is said in English (`TABLE_WORDS`, `tableWord`), which is what a script or the assistant gets. A field one schedule means otherwise has its own words, keyed `schedule.field`: a wall's area is its face, upright (`walls.area`, "Face area"), so that it is never read as a floor's.

**How it is drawn** (`tablePrimitives`): the title above, then a frame on white (its `style` fill, so it reads over a hatch) with a row of headings, a row per thing counted, at most `MAX_ROWS`, and the total; numbers set to the right of their column. The table of objects may have a column of symbols (`symbol`, a field of unit 'symbol'), which draws each thing counted as it is drawn on its own (its component, or its kind of object with the parameters it starts with, placed nowhere so that a door stands in no wall: `symbolPrimitives` in `kinds.ts`, handed to `tablePrimitives` so that tables need not import the kinds), fitted in its cell and kept in its own look (`own`), its rows made taller: the table is then the legend of the plan. The editor makes a table of objects with it (`newTable`); one with no `columns` of its own, as drawings before it hold, keeps the usual ones. Columns are as wide as the widest of their words, estimated from the number of characters, as text is everywhere in the core. A table stays upright and is moved by its corner; scaled, its text size scales.

**In the editor**: the object library has a section of tables under Drawing (`tableCards` in `WarehouseDialog.tsx`), each pictured counting a small house made for the purpose (`sample`), all at one scale; a card puts a table on the pointer (`Placing` of type `table`), which the place tool puts down once, selects and leaves. The Properties panel sets what it counts (resetting its columns, and its title when it had the usual one), the page it counts, its columns (ticked, each with the words over it), then how it is written.

### Components

The words, in the interface and here: a **component** is the reusable definition, edited from inside, every instance following; an **instance** is one placement of it; a **parametric object** is drawn from its parameters and has no inside to edit; the window that lists everything that can be placed, of both kinds, is the **object library**. A "component library" is only a drawing whose components are copied in (the bundled `.opencalque` libraries, File › Import).

**What the user sees is not that difference** (the owner's choice): to whoever draws, a radiator of 80 cm placed five times is one thing placed five times, as a component is, and one of 1.20 m another. A parametric object's **model** is its kind with every parameter, the defaults filled in (`variantKey` in `variants.ts`); `variantsOf` groups objects so and keeps, for each model, the parameters that tell it apart from the other models of its kind listed with it, by which `variantLabel` names it ("Radiator 800", "Radiator 1200", or "Radiator" alone when there is one). Only things placed in a building are models (`listedAsModel`): doors and windows (which cut walls), stairs (the category 'architecture') and what is written on the plan ('annotation', a north arrow) make the building or the drawing, are listed nowhere as entries and not counted among the objects placed; doors and windows have their own table. Nothing of it is stored. The editor's **entries** (`entries.ts`) are the components and the models together, an entry named by a component's id or "model:" and a model's key: the Components panel lists them in one list by name (a model with its picture, `parametricPicture` in `pictures.ts`, a click putting one more on the pointer with the same parameters, its pencil selecting its objects where most of them lie for the Properties panel to change them together, its trash deleting them after a question); the instance browser goes through an entry's placements; replacing works between any two entries (`replaceWithOps` in `components.ts`: an instance made another component's keeps its scale, a parametric object made another model takes its kind and parameters, and one made the other sort of thing is replaced by a node of that sort with a new id, in the same place, order and layer); the table of objects counts by model (`objectsOn`, `objectLabel`), its symbols drawn with their parameters. Changing a model's parameters moves its objects to another entry, or makes them one with it.

**What a component holds is on no layer, and an instance has no style** (since format version 2). Each placement gives the layer: its visibility, its lock, and its colour for what the component leaves uncoloured. `applyOps` refuses a `layer` on a node whose root is a component and a `style` on an instance; whatever puts nodes inside a component leaves the layer out (`layerIn` in `document.ts`, `layerHere` in the store for what the editor draws or places, `transplantOps` and `dxfOps` when the target is inside a component). A component placed inside another therefore takes the colour of the outer placement's layer.

`createComponent` moves the selected nodes under a new component node (shifted so the top-left of their bounds is the origin), takes them and what their groups hold off their layers, and leaves an instance where they were, on the layer of the first of them that had one. `detachInstance` does the reverse for one instance (Ungroup, on an instance): copies of the component's contents go where the instance drew them (moved by its insertion point, then mirrored, turned and sized about it with `transformOps`), on the instance's layer, and take its place in the stacking order; an instance with modifiers leaves a group that keeps them, so the drawing looks the same. The component stays in the drawing. `importComponents` copies components from another document with fresh ids, bringing nested dependencies along. A paste records `meta.source = "<sourceDocId>#<componentId>"` and reuses a copy already there, so that an instance copied and pasted back stays an instance of the same component; a library, or a drawing whose components are taken, is imported `fresh`: a component of the drawing's own each time, with no `meta.source`, named with a number after one already called so (`libraryOps`, `freeComponentName`). Instance nesting is capped at depth 8 when drawing.

**A placement may be stretched.** `scaleX` and `scaleY` on an instance stretch it along the component's own axes, on top of `scale`; `Transform` carries them and `applyTransform` / `inverseTransform` apply them before mirroring and turning, so everything that places a component's contents follows. A primitive that a stretch would no longer keep the kind it is (a turned ellipse stretched along an axis it is not square to) is drawn as a path (`transformGeometry` in `primitives.ts`); a text takes the stretch across its lines. On the canvas a single instance is resized by the frame a rectangle has (`resizeFrame` / `resizePatch` in `resize.ts`, which take the registry and the document for it): its box is that of what the component holds (`contentBox`, cached per drawing), a side stretches one way, a corner both, Shift keeps the proportions, the side held stays (`placedResize`), and the knob above turns it. The Properties panel offers "Back to its own proportions". Ungrouping a stretched instance (`detachInstance`) cannot keep what its contents are (a stretched turned rectangle is no rectangle): it gives the shapes it draws (`placedShapes`, `primitiveNodes` in `vectorize.ts`), in a group named after the component, what was uncoloured following its layer (`var(--layer)`). Editing a stretched instance's component in place, and pasting through it, use its uniform scale and ignore the stretch.

**Replacing placements with another entry** (`replaceWithOps` in `components.ts`): placements, instances of a component or parametric objects of a model, made placements of another component or model. An instance made another component's has its `component` changed and nothing else, so it stays where it is, turned, mirrored, scaled, stretched and on its layer, by its insertion point as blocks are replaced in CAD programs; a parametric object made another model takes its kind and parameters; one made the other sort of thing is removed and added again with a new id, where it was, turned, mirrored, on its layer and in its place in the stacking order. One inside the target component, or inside a component the target holds, is left as it was and counted as `skipped`, since a component cannot hold itself (`checkNode` would refuse it). The Components panel replaces all the placements of one entry (`replaceInstances`, the toast saying a component is placed nowhere any more, to be deleted if unwanted); the Properties panel of selected placements changes theirs (`InstanceComponent`, `swapSelectedComponent`), the components that would hold the one being edited not offered. Both pick from `EntryChoice`, the drawing's entries with their pictures, found by name. Two components drawn twice over, used here and there, so become one, and tables count them together.

**Going through the instances of a component** (`actions/instances.ts`, `InstanceBar.tsx`): the framed eye on a row of the Components panel, or `component.browse` on a selected instance (right-click menu), goes to each placement in turn (`instancesOf`: page by page in their order, then inside the components that hold some, each from top to bottom and left to right in rows of `ROW` mm). `showInstance` goes to its page, or into the component holding it, and into its group, selects it and brings it into the middle of the view at the same zoom when it fits (`bringIntoView`), so that stepping does not jump. Which component and which placement is kept with the windows over the editor (`useWindows`'s `browsing`), not in the store; the bar takes the place of the hints, says which of how many is shown, steps with its arrows or `component.nextInstance` / `component.previousInstance` (Alt+→, Alt+←, only while it is open), selects at once the placements where the editing is, and goes with its ✕ or Escape (the canvas's chain of Escape, after leaving a tool), leaving the one shown selected. A placement deleted meanwhile shows as "–", and stepping starts again from the first.

**Vectorizing a parametric object** (`vectorizeOps` in `vectorize.ts`, the command `component.vectorize`, in the Object and right-click menus): the shapes it draws (`parametricPrimitives`, with its own look laid over them, placed as it is placed) become a group in its place, with its name (or its kind's), place in the stacking order, layer and modifiers. It can then be edited shape by shape; what its parameters did is lost (a door made so no longer cuts its wall, which the toast says). It is not made a component: one who wants to reuse it makes it into one afterwards. A placed object hides what lies under it and a group does not, so the white of `objectBacking` comes along as white shapes in a group of their own ("White background") under the rest, which can be deleted; the drawing looks the same, as `placed-stretch.test.ts` checks against the SVG. A table of quantities is vectorized the same way (`tableShapesOps`): its frame, lines, words and symbols as they are drawn now become a group named after its title, with its layer and modifiers, which no longer counts anything (the toast says so); it looks the same (`tables.test.ts`). Hatches inside its symbols are left out, as they are for any vectorized shape.

**An instance has no look of its own.** What the component draws without a colour takes the colour of the layer the instance is placed on (`ink` in `KindContext`, set by the `instance` kind for its contents and inherited through nested instances), the way CAD blocks follow their layer. So a chair on a grey "Existing" layer is grey, while what the component colours itself keeps its colour. The Properties panel offers no stroke or fill for an instance and the eyedropper leaves instances alone: a look set on the instance would repaint the whole component and hide the component's own changes. To show one placement in other colours, change a copy of the component: placed from the object library again after it was changed, a library component comes in as the library has it, beside the changed one.

## 5. The editor

### State (`store.ts`, `navigation.ts`, `windows.ts`, `extensions.ts`)

One Zustand store, `useStore`, whose state is four groups declared apart in `store.ts`: the **session** (`doc`, `past`, `future`, `base`, `saved`, `file`, `page`, `scope`, `through`, `trail`, `selection`, `corner`, `activeLayer`, `view`), which opening a drawing replaces; the **interaction** in progress (`tool`, `placing`, the quick bar's locks, `drawStep`, `editingText`, the right-click menu, `status`…), which starts afresh with it; the **tool settings** (wall thickness and line, paper scale, the tool each toolbar button shows, the look of the next shapes, the dimension and annotation templates), which outlive drawings; and the `viewport`. `loadDocument` sets the first two and closes the windows, so nothing has to list what to keep. The windows laid over the editor and the toast are a store of their own (`useWindows` in `windows.ts`), and so is the version of the extensions in use (`useExtensions` in `extensions.ts`, which also holds the `registry`). Actions are plain exported functions, not store methods; going into and out of groups and components is in `navigation.ts`.

- **`scope`** is the container being shown and edited: a page, a group, or a component in edit mode. `page` remembers where to return to.
- **`through`** lists the instances double-clicked, outermost first, to reach the component being edited; null when it was opened from the library. `scopePath` turns `page`, `scope` and `through` into the way there (the page, the groups gone into, each component after the groups its placement is in), checking that each placement still leads on and giving up on the page otherwise. The breadcrumb (`Breadcrumb` in `Stage.tsx`) shows it; `leaveTo(id)` goes back out to any place on it, selecting what leads on from there and carrying the view back through the placements left, and `editComponent(null)` (Esc, the `component.finish` command) is `leaveTo` the place before the last. The breadcrumb has no Done button: every place on it is already the way out. Anything that changes how scope is entered should keep that way readable.
- **`trail`** is the deepest place left, as a `scope` and `through` of its own. `leaveTo` sets it to where it came out of, unless that was already on the way into the trail; `ahead(path, trail)` gives the places of the trail past the scope, only while the way to the scope leads into it through the same placements, and the breadcrumb shows them faint after it, on the page too. `returnTo(id)` goes back into one, carrying the view in through the placements as entering does. Entering anything off the trail, showing another page, a scope repaired by `settle`, or Esc on the page with nothing selected (`forgetTrail`) drops it; a trail whose places were deleted simply has nothing ahead. Code that sets `scope` goes through `editComponent`, `leaveTo`, `returnTo` or `showPage` so these rules hold.
- **`settle`** repairs state after any document change (scope still exists, selection still valid, active layer still exists). Every path that sets `doc` goes through it.
- **History**: every change goes through `record` in `store.ts`, which pushes a `Step` onto `past`: the document before it and the operations that made the change. `apply(ops)` reports a failure to the user, `applyOrThrow(ops)` throws it (the assistant's tools, which tell the model); there is no way to set a document without its operations, so the helpers of the core that build a result in several steps (`groupNodes`, `createComponent`, `importComponents`, `pasteNodes`…) return their `ops` beside it, and the editor applies those. `collapseHistory` merges steps and their operations. Undo and redo still restore documents (`Step.doc`); the operations are what a shared drawing would send (§10). Limit 200.
- **Gestures use preview/commit/cancel.** `preview(ops)` computes the result from `base` (the document when the gesture began) every time, without touching history. `commit()` records one undo step; `cancel()` restores `base`. Drags, handle edits, in-progress shapes and the object following the cursor in the place tool are all real documents produced this way, so there is no separate "ghost" rendering code.
- **Dirty** means `doc !== saved` by identity.
- **Recovery** (`recovery.ts`): a moment after each change a dirty drawing is copied into IndexedDB under this window's session id, and the window marks itself alive every five seconds. A window that closes normally (`pagehide`) or saves removes its copy; at start, copies of windows not alive for 20 s are offered in the welcome window. It works the same on desktop, whose window has IndexedDB too.
- **Faults in the interface** (`Guard.tsx`): the whole app, the drawing area and each panel are wrapped in an error boundary. The drawing lives in the store, outside React, so the fallback can always save it.

### Canvas (`CanvasView.tsx`, `draw.ts`)

`view` maps world to screen: `screen = world * zoom + (x, y)`, zoom in pixels per millimetre.

**How it paints** (`drawScene` in `draw.ts`), measured on a real plan of 1 200 objects, 5 800 paint steps, half of them the lines of hatches (the profile is a Playwright script driving Chrome's profiler, kept outside the repository; slowed four times on a screen of two pixels a point, hovering went from 54 slow frames in 60 moves to none):

- **The drawing is kept.** The desk, the sheets, the grid and the drawing are painted into a canvas of their own (`paintBase`), painted again only when the scene, the view, the size, the grid, the palette or a picture that arrived changes (`base.key`); each paint lays it down whole, then what moves with the pointer over it (snaps, the selection, sizes, guides, temporary dimensions). Before, every movement of the pointer painted the whole plan. Keep anything that changes with the pointer or the selection out of `paintBase`.
- **While the view moves** (a view that changed since the last paint; one that has not has stopped). **Panned** (`panBase`), the kept drawing is moved into a spare canvas and swapped with it, and only the strips that come into sight are painted (`paintBase` with a `rect`, clipped and culled to it), so that what lies outside shows as it comes in: laying the old drawing down moved and filling the rest with the desk, as first tried, left the edges blank until the drag stopped. It is moved by whole pixels of the canvas only, and kept for the view that makes (a fraction of a pixel off), since moving it by fractions on a screen of 1.5 pixels a point blurred it more at each step; it is laid down on whole pixels too, never blurred, and painted exactly once the view has been still for `SETTLE` (120 ms, `onRepaint`). **Zoomed**, it is painted whole at each step. Scaling the old drawing up while zooming in, and painting it sharp once the view stopped, was tried: it blurred and came back into focus, which read as the plan loading again, and the owner found it not worth the speed it gave slow computers.
- **Steps are grouped** (`paintSteps`): steps one after the other cut to the same outlines (the same arrays, a crop's or the shape a hatch is laid in) share one clip, and the lines of a hatch of one look are stroked as one path (`strokeHatch`): thousands of `save`/`clip`/`restore` became a few dozen.
- **What is out of sight is left out**, by each primitive's bounds (`extentOf`, cached per primitive), with a margin of 40 pixels. The paint order is worked out once per scene (`stepsOf`), not at each paint. A text smaller than half a pixel on screen is not drawn; a text is set at its own size and scaled with the view, as setting it at its size on screen made every step of zoom ask the browser for letters of a new size (tried, and slower).
- **React**: what changes with every movement of the pointer has a component of its own (`Status` in `Stage.tsx`), so that the tool bars are not drawn again; a list that goes through the drawing (`EntryChoice`) is made only while open.

**The view bar** (`ViewBar` in `Stage.tsx`) is a still square in the bottom right corner of the drawing, level with the tool bar (above the right end of its row when the drawing is too narrow for both, a container query on `.stage`), which opens upwards under the pointer, or while something in it has the focus (`:focus-within`, for a keyboard or a touch), into zoom in and out, a slider on the logarithm of the zoom (`MIN_ZOOM` to `MAX_ZOOM`, `zoomTo` in `actions/view.ts`), the zoom read as a drawing scale (`screenScale` in `view.ts`, at 96 CSS pixels to the inch; the exact zoom is in its `data-zoom`, which the browser tests read), zoom to fit, and the view settings as buttons lit while on (`VIEW_TOGGLES`, the preferences the View menu's commands switch). Open all the time, it took too much of the drawing; showing the scale on the square, it changed with every zoom and drew the eye.

`CanvasView.tsx` works out what to show (the scene, the handles and frame of the selection, labels), paints it, and dispatches the pointer: what a press does with each tool is `PRESSES` in `canvas/gestures/index.ts` (the two-point tools share `drawDown`), and what a movement and a release do during each kind of `Gesture` (`idle`, `press`, `move`, `handle`, `corner`, `marquee`, `draw`, `poly`, `turn`…, in `gesture.ts`) is `MOVES` and `RELEASES`. The gestures live in `canvas/gestures/` by family of tools (`select.ts`, `drawTools.ts`, `measure.ts`, `turn.ts`, `place.ts`). They share one `Canvas` object (`runtime.ts`), made once for the life of the canvas: the gesture in progress, panning (tracked apart so it can interrupt a drawing without losing it), the last pointer, and what the latest render worked out, which the component puts in it at each render. A movement fills in a `Shown` (the snap mark, guides, labels, status), which the canvas lays on its overlay and the status bar. Snapping is `aim.ts`, what is under the pointer `picking.ts`, what the drawing tools make `shapes.ts`. Handlers read fresh state with `useStore.getState()` rather than closing over render-time values. Escape, Enter and Space stay in `CanvasView.tsx`, with the wheel and the double-click.

Tools worth knowing about:

- **Dimension** takes three clicks: the two measured points, then a third that sets `offset` (gesture `offset`). While the tool is active and nothing is selected, the right panel edits `dimensionTemplate` in the store, which is spread into every dimension drawn next. The template and wall thickness are session settings: they survive opening another document but are not saved anywhere.
- **Measure** never touches the document. Its reading lives in the canvas overlay (`Overlay.measure`) and the status bar, and stays on screen until the next reading starts or the tool changes.
- **Walls and lines chain.** A `draw` gesture remembers where its run began (`origin`), how many segments it has, and when the last one finished. Clicking the last corner again ends the run; if that happens within 500 ms on a run of two or more walls (a double-click), a closing wall is added back to the origin. Arriving back at the origin by clicking it also ends the run.

- **The line tool** collects points in a `poly` gesture, and what it makes depends on how it ends (`finishPoly`): two points make a `line`, more a `polyline`, closed a polygon (a closed `polyline`). Enter, Esc, a tap on Space or switching tool keep what was drawn open. A click back on the last point (within `SAME_POINT` px of it or of where the last click landed, so snapping cannot turn the wobble of a double-click into a tiny segment) ends it, and closes it when that second click comes within 500 ms; a slower double-click still closes it through the system's `dblclick` (`endedLine`). Coming back within 10 px of the first point closes it too. The run of walls ends and closes the same way (`ended`). There is no separate polyline tool: the line tool used to chain separate `line` nodes, which nobody wanted.
- **Typed sizes.** `QuickBar.tsx` floats above the toolbar while a shape tool is active. What is typed goes into `drawLocks` in the store (`a` and `b`: width and height, or length and angle), and `constrain()` in the canvas applies them on top of where the pointer is, so a typed size wins and the pointer still chooses the rest. The bar talks to the canvas through `canvas/drawing.ts` (`commit` on Enter, `refresh` after a keystroke), because the gesture lives in a ref inside the canvas. Pressing a digit while a shape tool is active focuses the bar's first field. Locks are cleared after each shape and on every tool change.
- **The look of the next shapes.** Beside the sizes the bar has the colour of the lines of the next shapes (`drawColor` in the store; none means the layer's, which the swatch shows as it is, marked with the layers sign) and, for the tools that make closed shapes (rectangle, ellipse, and the line tool, whose closed shapes are polygons), their fill (`drawFill`, `drawPattern`), in the same windows as the properties (`currentStyle` in `canvas/shapes.ts` gives a fill only to a closed shape). Weights and kinds of line are set afterwards, in the properties: the bar once had them too, with dots of ready-made colours of which the first, drawn black, meant the layer's colour. With nothing selected the eyedropper sets the colour and the fill shown there.
- **Size labels** beside the shape being drawn, or the one selected shape, are part of the canvas overlay (`Overlay.labels`, `Overlay.angle`), not of the drawing.
- The plain shapes (`SHAPE_TOOLS`) share one toolbar button showing `shapeTool`, the one used last.

A press counts as dragging out a shape only if the pointer moved more than 12 px and the button was held more than 200 ms (`DRAG_DISTANCE`, `DRAG_TIME`). Anything less is a click, so a hand that slips while clicking the first point does not leave a stub and end the run, which it once did.

- **Text is typed in place.** A click with the text tool previews an empty text and sets `editingText` in the store; `TextEditor.tsx` puts an input exactly over it (the canvas leaves that one node out) and previews every keystroke. `finishTextEdit` (in `actions/edit.ts`) commits, or cancels when the text was left empty. Double-clicking a text edits it the same way.
- **Axis guide.** While a line, wall, polyline segment or measurement is exactly horizontal or vertical, `Overlay.axis` draws a guide across the whole view through its start point.
- **Hints and fields follow the step.** The canvas publishes how far the shape in progress has got as `drawStep` in the store (0, then the number of points placed; `syncStep` is called after every event that can change the gesture). `hintsFor` in `tools.ts` turns tool and step into the next thing to do plus only the keys usable right now, and `QuickBar.tsx` shows a length and an angle only once there is a point to measure them from. When a tool gains a key, add it to `hintsFor` at the step where it starts to apply.
- **Toolbar.** Door and window have their own buttons (`PlaceButton`, present only when an extension in use provides the kind); everything else that can be placed is behind the object library button.

**Units (`units.ts`).** Drawings are in millimetres whatever the user chose. `units.ts` is the only place that converts: `formatNumber` / `formatLength` to show, `parseLength` to read (a bare number is in the chosen unit, a suffix such as `cm` wins). Length fields use `Field`'s `length` prop; parameters of parametric objects are converted when their `ParamDef` has `unit: 'length'`. The unit is a preference, so changing it remounts the interface, as the language does. New dimensions take the chosen unit; existing ones keep theirs. The grid steps stay metric.

In the quick bar, a size field that is focused and still following the pointer is shown empty with the moving value as a placeholder, so that what is typed never gets appended to a number that changed under the caret.

**Snapping (`snap` in the canvas, `snapTo` in `packages/core/src/snap.ts`).** Alt disables it; Shift holds the direction to the nearest 45° from the previous point and still lines up with what is drawn, as an arrow key does (`heldLine`, below); otherwise `snapTo` looks within 10 px of the pointer, and failing that the grid is used. The grid step adapts to zoom (`gridStep`). `snapTo` works from the scene alone and offers, nearest first and the more specific first when equally near: a point (what a kind gives in `snapPoints`, and the corners of its lines), a crossing of two lines, the middle of a straight line, the foot of the perpendicular from where the line being drawn started; with none of those, the place upright from one point and level with another, both within reach (`aligned`), with a guide from each (`Snap.guides`, shown as smart guides). Those points are only the `aligners` given to `snapTo` and the start of the line being drawn, never every point drawn, which in a full plan lined up almost anywhere: the editor gives the points the pointer rested on (snapped to as a point, a middle or a crossing for `REST`, 250 ms, then left), the last `TRACKED` (3) of them, kept on the canvas in `tracked` and drawn as small crosses, forgotten when the tool changes, on Escape and at the end of a drag (`trackedPoints` and `rest` in `aim.ts`); then the nearest place on a line, taken at the grid step along it when the grid is on; then a place upright or level with one point, the grid saying where along. The lines of an item are the paths it draws (`snapLinesOf`), unless its kind says otherwise with `snapLines`: a wall adds its middle line to its faces, and dimensions, annotations, rooms and pictures give none. Two rules keep curves from flooding it: a point where a line turns by less than 12° is a point of a curve, not a corner, and only a stretch between two corners has a middle. Strokes flagged `texture` (hatching, fill patterns) are never snapped to. The mark drawn at the pointer tells the kind (`Overlay.marker`).

**Holding a direction (`axisLock` in the store, `lineEnd` in the canvas).** While a line, wall, divider or polyline has its first point, the arrow keys are the commands `draw.lockLevel` and `draw.lockUpright` (listed before the nudge commands, which need a selection; their `when` is `drawingLine`). They set `axisLock` and ask the canvas to redraw through `drawing.refresh`. `lineEnd` then keeps the end on that line through the last point (`heldLine`, which Shift goes through too, at its 45° direction): if the pointer snaps to a point, a middle or a crossing elsewhere, the end is that place brought onto the line, and `Overlay.link` draws a dotted line between the two; otherwise it is `alongLine`, by grid steps (the pointer as it is with the grid off) and stopping where the held line crosses a line near the pointer: a wall's line, or anything drawn, the faces of walls, the lines of a traced plan and the sides of shapes included (with snapping to objects off, none of this). The lock is let go when the segment is finished, the tool changes or the gesture is abandoned. Typed lengths still apply on top. Only level and upright can be held, not the direction of an existing line. The same two commands apply while something is dragged with the select tool (`dragging`: a preview is in progress): a move keeps only that part of its displacement, lining up still deciding how far, and a dragged handle or wall corner goes through `lineEnd` from where it was. Shift on a dragged end or corner (`heldNearest` in `aim.ts`) holds it to the nearest to the pointer of: the line of the wall it is the end of (each wall's, at a corner), and the level, upright and 45° lines through the other end of each, which brings a slanting wall level or upright. Before the pointer has moved there is no preview yet, so the arrows still nudge.

**Measuring never takes the grid** (`MEASURING` in the canvas: dimension, measure, angle). `snap` gives their points the objects' points, middles, crossings and lines, and otherwise the pointer as it is. Shift holds the direction from the first point to 45° steps through `heldMeasure`, which is `lineEnd`'s idea for measuring: a point pointed at elsewhere is brought onto the held line (with its `link`), otherwise the point stops where the held line crosses a drawn line near the pointer, any path of the scene (wall faces, sides of shapes) rather than only wall middles, since a dimension measures to what is drawn.

**Splitting a wall (`splitWall` in `actions/walls.ts`).** The command `wall.split` cuts the one selected wall with `splitWallOps` at `menuPoint`, the place of the last right-click, which the canvas records with the context menu; when that point is not on the wall (the command came from the menu bar or the command list) the wall is cut in its middle. It is in the Edit menu and the command list, not in the right-click menu: on the drawing, the Split tool does it, showing where.

**Smart guides (`alignMove`, `moveGuides` in `snap.ts`).** When a move begins, the canvas takes the box and snap points of what is moved and of every other thing in view (`alignables`). A group counts as itself and as each thing it holds, however deeply (`heldItems` in `scene.ts`), so that a thing lines up with one wall of a plan whose walls were grouped; what is moved is left out, even from inside a group, and a group holding more than 2000 things in view counts by its box alone. On each movement `alignMove` adjusts the displacement, each axis on its own: sides and middles of boxes against those of other boxes, points against points (never one against the other, or something would always be in reach), and the places where the moved thing would keep the same gap as its neighbours. An axis with nothing within 6 px goes by the grid as before. `moveGuides` then reports what is true of where things now are, lines and equal gaps, for the overlay (`Overlay.smart`); it does not care how they got there, so things lined up by the grid show too. Both are pure and unit-tested. Not done: the same while drawing or resizing, and objects that are turned (boxes are upright).

**Offsetting** (`offset.ts`, `gestures/offset.ts`): a copy parallel to a line or a shape. What that means is each type's (`parallel`, `beside` in `kinds.ts`), a type without them is not offset, and the copy is `cloneOps` plus a patch, so it keeps the look and the layer. `parallelPath` joins moved sides where they meet; it does not trim a shape that folds over itself, as AutoCAD does, but refuses it (a side running backwards, a path coming to cross itself). A curve keeps its points, moved straight out from it (`smooth`): exact at them, very nearly so between, and still a curve to edit. The tool's gesture is not called `offset`, which is a dimension's third point, but `parallel`.

**Selecting by a box**: dragged to the right, `itemsInside`; dragged to the left, `itemsTouching`, which means what a click somewhere in the box would pick up (`primitiveTouches` follows `distToPrimitive`): the lines of a shape and the inside of a filled one, of a component or an object all of it, never a floor or the inside of a sheet. It goes by what is drawn, not by bounds, or a long diagonal would be taken by any box near it.

**The layer in use** is the editor's, not the drawing's: choosing one is no edit, takes no step of undo and leaves nothing to save. Only what is written carries it, as `meta.activeLayer` on a copy (`forFile` in `store.ts`, used wherever the editor writes a drawing), and only when it is not the first; `session` opens on it when that layer is still there. So a layer chosen and left with no change made is not remembered.

### Commands and shortcuts (`commands.ts`)

Every action the user can trigger is a `Command` (`id`, `title`, `category`, default `keys`, `run`) returned by `allCommands()`. That list is the static commands plus ones generated from the current state: one per parametric kind, component, page, and extension command. The palette, the window key handler (`handleKeyDown`), the main menu and the toolbar tooltips all read from it, so **adding a command means adding one entry to `STATIC`**; nothing else needs touching for it to be searchable and rebindable.

- Shortcuts are strings like `Mod+Shift+S`, where `Mod` is Ctrl, or Cmd on macOS. `eventKey` builds them from a key event: letters follow the keyboard layout (`e.key`), digits follow the physical key (`e.code`) so `Shift+1` works on AZERTY too.
- The user's changes are kept as `overrides` (command id → list of keys, empty meaning none) in `localStorage` under `opencalque.shortcuts`. They belong to the browser profile or desktop install, not to the document. A key belongs to one command: assigning it removes it from whichever command had it.
- The overrides can be exported to a JSON file (`"format": "opencalque-shortcuts"`, `version` 1) and imported back, which replaces them (`shortcuts.ts`). Import keeps commands it does not know (an extension may not be loaded yet), leaves out what cannot be a key, caps how much it reads, and gives each key to one command (`settleShortcuts`).
- `when` gates a command; a command whose `when` is false is skipped, which is how `R` rotates while placing and otherwise selects the rectangle tool (`place.rotate` is listed before `tool.rect`).
- `global` commands also work while typing in a field; the rest are ignored there so text editing keeps its native shortcuts. A field that takes no text does not count (`forTheField`): a checkbox keeps no key, a slider only those that move it, so Ctrl+Z works right after either was used.
- `interrupts` commands make the canvas abandon the gesture in progress (it listens through `onCommand`).
- **Escape, Enter and Space are not commands.** The canvas handles them directly because their meaning depends on the gesture in progress, and they cannot be reassigned. A command may still be bound to a key with Space (`edit.flipSide` is `Shift+Space`): the canvas asks `commandFor` first and leaves the key alone when a command takes it, so it neither pans nor finishes the drawing.

### Dropped files (`drop.ts`)

Files dragged onto the window from outside are routed by extension in `openDropped`: a picture or a PDF goes to `placeFloorPlan` (centred where it was dropped, then calibration starts), an `.opencalque` file is opened, and a `.json` file is opened as a drawing or installed when it is a declarative extension. `DropTarget` in `App.tsx` listens on the window in the capture phase, because the docking library handles drag and drop of its own and would otherwise swallow the files; the assistant's message box is left to take pictures itself. A dropped drawing has no place to save back to, so the first save asks where.

### Floor-plan import and calibration (`floorplan.ts`)

`importFloorPlan` reads a file through `Platform.openBytes`, turns it into a canvas (pictures through `createImageBitmap`, PDFs through pdf.js, first page only), and adds an asset plus an `image` node on a layer named "Reference", at the bottom of the stacking order (so under the walls, and the floors, drawn over it) and 60% opaque. The initial size is a guess: a PDF knows its paper size, so it is placed as if drawn at 1:100; a picture is placed 10 m wide.

pdf.js is imported dynamically so it stays out of the main bundle, and its worker module is loaded onto the main thread (`globalThis.pdfjsWorker`) instead of started as a worker, because a desktop app loaded from `file://` cannot reliably start one.

The **calibrate** tool reuses the measure gesture without snapping (a scan has nothing to snap to) and stores the two picked points in `store.calibration`. The right panel then asks for the real distance; `applyCalibration` scales the picture about the first point by `real / measured` and locks it. `parseLength` accepts `3500`, `350 cm`, `3.5 m` and a decimal comma.

### The assistant (`ai/`)

The assistant edits the drawing by calling tools, in a loop that ends when the model stops asking for them.

- **`agent.ts`** is the provider-neutral core and has no dependency on the store or the DOM, so it is unit-tested with a scripted model. `systemPrompt` describes the format (it embeds the JSON Schema of a node, generated from the Zod schema, and the registered parametric kinds) and how to edit. `describeState` is prepended to each user message, inside `<drawing_state>`: where the person works (page, or a component or group opened to edit), the active layer, the part of the drawing on screen, the **selection**, and the drawing as JSON when it is under 40 000 characters, otherwise a summary. The tools are those of every agent, and live in the core (see "Agents" below); `runTool` runs them on the editor through `drawingHost`, one after the other since each may change what the next sees, and says what happened to the person in their language (`noteOf`). `toolsFor` leaves `view_drawing` out for a provider that cannot be shown pictures, and `systemPrompt` then does not mention it.
- **The selection is context, as a selection in an editor is for a coding assistant.** `describeSelection` writes a `<selection>` block: each selected node in full (and what selected groups hold), with what it measures (`measure`: a wall's length and thickness, a room's area, an instance's component, where each is drawn), or the selected wall corner with the walls that meet there and how. Above 20 000 characters the nodes are listed by id and the model reads them with `read_document`. The composer shows a label for what will be sent (`useSelectionLabel` in `AssistantPanel.tsx`) with an × that leaves it out of one message (`RequestContext.selection`); the label comes back when the selection changes. The block is inside `<drawing_state>`, so `shorten` drops it from stored conversations like the rest.
- **`types.ts`** is the seam. A `Provider` creates a `ChatSession`, and **the session owns the conversation in the provider's own format**. That is deliberate: Claude's reasoning blocks must be sent back unchanged, which a lossy neutral history could not guarantee.
- **`anthropic.ts`** uses the official SDK in the browser (`dangerouslyAllowBrowser`), streaming, with adaptive thinking, `effort: 'medium'`, prompt caching, eager tool-input streaming, and server-side refusal fallbacks (`fallbacks: 'default'`). Which of those a model gets is a table, `CLAUDE_FEATURES` (`modelOptions`): Claude Haiku 5.5 takes thinking and effort but has no server-side fallback, and a model not listed (one chosen in an older version) gets a plain request. A step that ends in a refusal, or runs out of output mid tool call, is dropped rather than run.
- **`compatible.ts`** covers every other provider, including Ollama, through the OpenAI chat-completions format, not streamed. It is handed an `Http` function: on desktop that is `platform.request`, elsewhere `fetch`.
- **`claudecli.ts`** uses the Claude Code CLI as a model. The CLI answers in text only, so tools are carried in the text: the prompt explains that a call is written as an `<opencalque-tool>{…}</opencalque-tool>` block, `parseReply` extracts them, and results go back in the next prompt of the same CLI session (`--resume`). The main process (`runClaude` in `apps/desktop/src/main/index.ts`) spawns `claude -p --output-format json --restricted --strict-mcp-config --disable-slash-commands` in an empty folder of its own (`assistant` in the profile), the same every time because the CLI keeps its conversations by folder and `--resume` finds one only there, with the prompt on stdin and every argument fixed or validated, so no user text reaches a command line and the CLI has nothing to act on. It cannot be shown pictures.
- **`chat.ts`** holds the conversations and the session of the current one, and calls `collapseHistory` so that all the edits of one request are a single undo step.
- **Conversations are kept** (`opencalque.chats` in local storage, the 30 most recent). A conversation outlives its session: `ChatSession.snapshot()` returns the history in the provider's own format, made small enough to store (`shorten` drops old copies of the drawing, pictures become a note, Claude's reasoning blocks are dropped because they are only valid in the unchanged conversation that produced them), and `createSession({ history })` takes it back. `currentSession()` in `chat.ts` makes a new session whenever the settings changed or a conversation was reopened: with the snapshot when the provider is the same (so **changing the model keeps the conversation**), otherwise with a plain transcript sent along with the next message. Switching conversation is refused while a request is running.
- **Pictures.** `TurnInput` carries `images`; `pictures.ts` scales what was pasted, dropped or chosen to at most 1568 px JPEG and makes a small preview, which is all that is stored. `Provider.pictures` says whether the provider can take them (the CLI cannot).
- **Slash commands and the model picker** live in `AssistantPanel.tsx`: text starting with `/` is never sent to the model; it drives a list (`/new`, `/resume`, `/model`, `/clear`, `/help`). `listModels` asks Ollama and compatible services for `GET {baseUrl}/models`.

Calling the provider straight from the app with the user's key is right for a local app. A hosted version must not ship keys to browsers: add a provider that calls your own server.

The production Content-Security-Policy (`apps/web/csp.ts`) therefore allows `connect-src` to any `https:` host and to localhost.

### Agents (`tools.ts`, `check.ts`, `cli/src/mcp.ts`, `desktop/src/main/bridge.ts`)

One set of tools serves the assistant, outside agents on files, and outside agents on the open drawing: `DRAWING_TOOLS`, run by `runDrawingTool(name, input, host)`. The tools know nothing of where the drawing is; a `DrawingHost` says (`doc`, `scope`, `apply`, and `picture` when it can draw). Each result carries a `note` saying what happened, for a host to tell the person in its own words: the core speaks no language but the English a model reads. **A new tool goes here**, so that every agent has it, and `drawingGuide` says how to use it. What is told to the assistant alone (the selection, what comes with each message, how to talk to the person) stays in `systemPrompt`.

- **`apply_operations`** validates with `parseOps`, is all-or-nothing, and reports the ids added, `unknownProperties`, and `problems`. **`read_document`** gives all of the drawing, a container, or chosen `ids`, without assets. **`describe_drawing`** is the short account that an agent outside the app needs in place of the `<drawing_state>` block. **`view_image`** shows a picture placed in the drawing, with the pixel-to-millimetre mapping.
- **`view_drawing`** shows a page, or an `area` of it, as `toSVG` draws it, and says what the picture covers: 1568 pixels on its longer side, PNG since a plan is thin lines on white. The host draws it: the browser in the editor (`svgToCanvas`, which the PNG export uses too), `resvg` outside it (`render.ts`). resvg knows no `non-scaling-stroke` and sees only the fonts it is given, so `weighted` writes line weights in millimetres for the size of the picture, and it is given the fonts in `fonts/`. It stays out of the core, and out of the app: it is a dependency of the CLI alone.
- **`measure_drawing`** is `quantities`, by part (`of`), and says how much there is rather than sending more than 40 000 characters. **`check_drawing`** is `checkDrawing`.
- **`applyEdit`** is `applyOps` with what follows from an edit (`openingFollowOps`), and is what the store, the CLI and the MCP server apply, so that one list of operations makes one drawing wherever it is applied. A new effect of an edit goes there. `applyOps` itself stays what the operations say and nothing more.

**Finding a command (`commandSearch.ts`).** The command list keeps what matches every word typed, and puts the closest first, so that Enter runs what was typed: a whole word before the start of one before the inside of one, and in the title in the person's language before anywhere else. The English name of a translated title counts as a keyword.

**The check (`check.ts`).** A model cannot see that a room came out wrong, and `apply_operations` used to say only that it was valid. `checkDrawing` reports what is nearly always a mistake, and says what to do about it; `problemsMadeBy` is what an edit made, by comparing the problems of the pages it changed before and after it, so that an agent is not told of what the person left as it was. Every problem must stay silent on plans that are right: `check.test.ts` puts a room in every cell of 200 random plans and runs a real one. Two findings from that test are built in:

- **A wall end is only a gap on a page where a room did not close or two ran into one.** Walls stand free for good reasons, and a stub close to a wall on a real plan looks the same as a mistake. So `wall-gap` is a reason given for a room problem, not a problem of its own.
- **Closer than `GAP` is not a gap.** Rooms take walls closer than that as touching (see "Rooms"), so a wall a hair short closes its room and must not be reported. From there to `WALL_GAP` (about a wall's thickness, what is lost by mistaking a face for a line) it may be why, measured across the whole end of the wall, since a wall drawn by a face can touch by the other one. Nothing here is a rule of what rooms are: `roomAt` decides that, and the check only explains it.

**The MCP server.** `mcp.ts` puts the tools behind the protocol with the SDK's low-level `Server`, since they already have their JSON Schemas, and adds `read_guide`, as not every client passes on a server's instructions. The guide leaves out the schema of every node, seven parts in eight of it, as Claude Code saves a tool result above 25 000 tokens to a file rather than show it, and warns above 10 000: it names the types, and `read_guide` with a `type` gives the schema of one (`nodeTypeSchema`). The assistant, whose prompt is cached, still has it whole. Nothing but the protocol may reach stdout, hence `pnpm --silent`. A `Backend` says where calls go:

- **`fileBackend`** (`mcp-files.ts`) reads the file again for each call, so that what someone else saved is what is edited, and replaces it whole after each edit (`writeDrawing`), so that it is never half written. `open_drawing` chooses the file, and takes only the extensions of drawings: an agent cannot be talked into overwriting anything else. There is no undo, and no lock against the app saving over it.
- **`liveBackend`** forwards every call to the desktop app, which runs it in the editor (`ai/bridge.ts`) on the host the assistant uses (`openDrawing`), so an edit is a step of the undo through `applyOrThrow`.

**The app as a server (`--mcp`).** Someone who installed the app has no Node and no checkout, so the app is the server: `agentCommand` says what to run, Preferences shows it, and `index.ts` then opens no window, uses a profile of its own in the temporary folder so as to leave the running app's alone, and loads `mcp.ts` (a chunk of its own, so that a normal start does not pay for it). It serves the live backend only, as files need `render.ts`, a native module. **It must not take a script or a path.** The shipped program has `runAsNode` switched off (`after-pack.cjs`) so that it cannot be borrowed to run other code, which is why this is a mode of the app and not `ELECTRON_RUN_AS_NODE`; do not turn that fuse back on for it. `--mcp` runs this one fixed thing, and can do nothing a program holding the token could not. Three things are particular to Electron, all found on the packaged app on Windows and none visible from Node: `process.stdin` in the main process is an empty stream that ends at once, so the real pipe is read from file descriptor 0; `app.quit()` then waits for that read for ever, so it leaves by `app.exit`; and Electron itself writes an empty line to stdout before any code runs, which cannot be stopped and which clients skip as not being a message. A portable app and an AppImage run from a copy that goes away, so `agentCommand` gives what the person started (`PORTABLE_EXECUTABLE_FILE`, `APPIMAGE`).

**The door of the desktop app (`bridge.ts`).** It can change the person's drawing, so it is off until they turn it on (the `agentBridge` preference, in the Agents section of the AI page of Preferences, shown only where `platform.agentBridge` exists), and turned off it leaves nothing listening. It listens on 127.0.0.1 on a port of the system's choosing, with a new 256-bit token each time it opens, both written to `~/.opencalque/bridge.json` (`OPENCALQUE_BRIDGE_FILE` moves it, for tests). A web page can reach a local port, so anything with an `Origin` is refused before the token is looked at. Any program the person runs can read that file: the door keeps out other computers and web pages, not their own programs, which is why it is a choice and why the preference says so. The file is removed when the door closes or the app quits; one left by a crash is found out by the refused connection. The path is written in both `bridge.ts` and `mcp.ts`, which share no package; a test keeps them equal.

### Menu bar and preferences

Edit holds only general editing (undo, clipboard, select); what is done to the selection as an object (group, order, turn and flip, modifiers, components) is in the Object menu, and the right-click menu offers just the most used of those (not turning and mirroring, which are in the toolbar), each by its `short` name where the title says "selection" (it is plain that the menu acts on what was clicked), leaving out what does not apply to what was clicked (Ungroup on a wall, Make into a component on a component) where the menu bar greys it. `Preferences.tsx` is a list of pages on the left (`PAGES`: general, drawing, AI, keyboard shortcuts, extensions) and the chosen page on the right; adding a page is adding a line there. The shortcuts page lists every command and records new keys in place, with the same rules as the command list. `MenuBar.tsx` defines each menu as a list of command ids (null for a separator, `@Category` for every command of a category), so menus need no logic of their own: a command's `when` disables its item and `checked` shows a tick. Preferences live in `prefs.ts` (`localStorage` key `opencalque.prefs`); each AI provider keeps its own key there so that switching providers can never send one provider's key to another. Only what differs from the defaults is stored (`storedPrefs`), each provider's settings one by one, so that a default changed in a later version (the assistant's model, a setting turned on) reaches everyone who never chose otherwise; the unit, whose default is guessed from the system's language, is kept once chosen. `prefs.test.ts` checks it, and reading what an older version stored whole.

**Licences.** `THIRD-PARTY-NOTICES.txt` at the root holds the licence of every package of others that the web build holds and of the fonts that ship (`apps/web/scripts/notices.mjs`, `pnpm notices`, which runs the real build and lists the packages its modules come from). About shows it under Licences, loaded only then; the installers carry it. CI fails when it no longer matches the build (`pnpm notices --check`), so a dependency added or updated means running `pnpm notices` and committing the result.

**Dragging numbers.** `scrub()` in `ui.tsx` lets any numeric `Field` (and the quick bar's thickness) be changed by holding Alt and dragging sideways; Shift is ten times faster, `min` stops sizes at zero, and `collapseHistory` makes the whole drag one undo step. `watchScrubKey` sets a class on `body` while Alt is down so those fields show a sideways arrow.

**Selection box.** Several selected objects get one box around them all (`sceneBounds`), and anywhere in that box is the selection: a right-click there is about it, and a press there on no object drags it all (`press` with `beside`), letting it go only if released without moving. This holds wherever the box is shown (`gripBox`), so not for one object that has handles of its own. A selection box can therefore not be started from inside the box of a selection; click first to let it go.

**Autosave (`autosave.ts`).** With the `autosave` preference on (the default), a drawing that has a file is written to it two seconds after the last change, never in the middle of a gesture. A drawing with no file yet, or opened in a browser without the File System Access API (its `token` is null), is left alone. The menu bar shows "Saved" beside the name.

**The bundled libraries** are generated by `pnpm warehouse` (`packages/cli/src/build-warehouse.ts`) from short definitions of each symbol, millimetres from its top-left corner, the side that goes against a wall at the top. A component is known by its place in its library (`bathroom_3`), and a drawing that imported it recognises it by that (`meta.source`): add new components at the end of a library, never in between, and leave the place of one taken out empty (`null`), as the bathroom's washbasin left `bathroom_2` and its bathtub `bathroom_3` when they became parametric objects, and the kitchen's sink unit, hob and fridge `kitchen_2` to `kitchen_4`. A fitting or a piece of furniture that replaces a component of a library goes in the built-in extension (`ext-architecture`), not in a declarative one: those that ship with the app are installed only when someone installs them, so a library component replaced by one would be gone for everyone else. `PLACES` in `apps/web/src/catalog.test.ts` lists every place ever given and fails when one changes hands: `bathroom_5` held a double washbasin while it was being made and the wall-hung toilet in 1.0.0-rc.3, so drawings hold either under it, and it stays empty. Its shapes have ids of their own derived from it, so the generated files change only where the definitions do.

**How the symbols are drawn.** Each is drawn as it is seen from above, with what tells it from another: the cushions and arms of a sofa, the pillows and turned-back duvet of a bed, the curved backrest of a chair, the five casters of an office chair, the cistern and seat of a toilet, the burners of a hob, the hangers in a wardrobe. Outlines are at the usual weight and what lies within them is thin (`thin`, 0.5, the weight `ext-architecture` gives its details); a curved or soft outline is rounded (`roundRect`, `rounded`, `band` for a curved bar with round ends, `bowl` for the shape of a toilet), with `roundCorners` from `geometry.ts`, which a declarative extension also uses for a `path` with a `radius`. A placed component backs every closed shape of its own with white, all the backings under all the lines (`OBJECT_FILL` in `kinds.ts`), so shapes that overlap show each other's lines: the parts of a symbol touch rather than overlap, and what one part hides of another is left out when drawn (`uncovered`: the legs of the office chair are drawn only where the seat does not cover them). Bigger symbols are built from smaller ones (`placed` sets a chair round a table, turned). Redrawing a symbol in its place is fine; a drawing that took the old one keeps it, since it holds its own copy. `pnpm warehouse:gallery [file]` draws every component and bundled parametric object on one page at one scale, to look them over after a change.

**Components panel** (`Components` in `LeftPanel.tsx`), a tab beside Layers and Pages: the components of the drawing, as a list or as pictures side by side (the preference `componentsView`, switched in its heading), each with a picture (`toSVG` of the component, drawn from `base` during a drag so that it is not redrawn at every move) and its placements where the drawing shows them (`componentPlacements` in core: on a page, or inside a component itself placed so, each placement counted once). A click puts it on the pointer and a drag puts it down on the drawing (`carry` in `carry.ts`, shared with the object library); a double-click on its name renames it (the first click having put it on the pointer, the double-click takes it off); its pencil opens it with what it holds filling the view (`openComponent` in `actions/view.ts`, which the object library and a paper's "on every sheet" use too: leaving, by whatever way, brings back the view and the selection it was opened from); its bin deletes it with its placements once the user has said yes (`deleteComponent`, through `ask`). Making a component is not offered there: it is done to a selection, from the Object and right-click menus. One placed nowhere (`unusedComponents`, which also takes those placed only inside unused ones) is faint, and the panel's "···" (`MoreMenu.tsx`, a list of what a panel offers besides its rows), like the command `component.purge`, deletes them all after asking. A row is highlighted when a placement of its component is selected.

**Asking first** (`ask` in `windows.ts`, `QuestionWindow.tsx`). What takes more away than it seems (a component with all its placements, the unused components) asks in a window of the app: a title, what will go, Cancel, which has the focus so that Enter does nothing unseen, and the action in red. Escape and a click beside it are Cancel. Discarding unsaved changes still asks with the browser's `confirm`. What is on every sheet, a component too, is left out: it is not placed, and is edited from a paper's properties. A search field above the list narrows it by name. The object library does not list them: it is what can be brought in, and the panel what the drawing holds, so that there is one place for each.

**Object library.** It is in sections, listed down its left side under headings, each with how many things it holds (`HEADINGS` in `WarehouseDialog.tsx`: Rooms, in the order of a home, Building, Drawing; a section of any other name, a library from a web catalog for instance, comes after them under Others, and "Other objects" last), with, at the foot of the list, where more comes from: a drawing on this computer, whose components are copied into the drawing (`importLibraryFrom`, after which the window closes and the Components panel shows them), and a web catalog, whose address opens there; there is no footer under the cards; in a window too narrow for the list the sections are a `select` beside the search. A search looks through every section whatever section was chosen, the list counting what each one found; a section chosen while searching narrows it and is not remembered, and the library comes back to its section when the search is cleared. Each card is one picture, a name and one line (a library component's description, a parametric object's default size in the user's unit from its `box` or `size`), cut short where it is longer; its tooltip has the rest, a parametric object's description among it. A card is clicked to put what it holds on the pointer (the place tool), or dragged onto the drawing (`carry`). A component of a library is not copied into the drawing then: the placing (`type: 'library'`) carries the library, and the place gesture adds the copy (`libraryOps` in `actions/file.ts`, worked out once per drawing in `fromLibrary`) in the same preview, and so the same undo step, as the first placement, so that a placing given up leaves nothing; once it is there unchanged, later placements reuse it. Dragged, once the pointer has moved five pixels with the button held, the window closes and the same placing starts, `carried`; the canvas puts it down where the button is let go over it, selects it and goes back to the select tool, and let go anywhere else it stays on the pointer, `carried` turned off, as after a click. A card's picture is not draggable, so the browser never carries it as an image file, which the window's drop handler would take as a plan to trace. The window has no Done button, nothing being confirmed in it: a cross in its corner, Escape and a click beside it close it. A library's catalog entry may say the room each of its components is for (`categories`, by component id: `living`, `dining`, `bedroom`, `office`, or any section of its own), and those components are listed under that room rather than under the library's name, which shows only for the components that say none: the furniture library is listed as Living room, Dining room, Bedroom and Office, while its components keep their places in it. "Add all of these" ("Add the whole library" when it is), beside the name of the section, copies the components of one library a section shows. Parametric objects are listed among the components of their kind, not in a group of their own: a kind says its `category` (`ParametricKind.category`, `category` in a declarative extension), a room, one of the bundled libraries' ids (`furniture`, `bathroom`, `kitchen`, `electrical`) to be listed with it, or `architecture` (doors, windows, stairs, listed under Building) or `annotation`; a kind that says none is under "Other objects". Their cards carry a small badge in the corner, whose tooltip says they are parametric. `WarehouseDialog.tsx` is two separate windows sharing a frame, chosen by `warehouse` in the store: the object library and Extensions. Components of the drawing are renamed, edited and deleted from the Components panel only, and a remembered layout that still names a retired panel is cleaned by `withoutUnknownPanels` in `Layout.tsx`. A library's catalog entry may carry `translations` (as extensions do); the bundled ones are generated with French, Spanish and German, and a component is given its translated name when it is copied into the drawing. The library lists everything that can be placed in one searchable grid: the parametric objects of the extensions in use (pictured with their default sizes, doors and windows in a piece of wall), and those of every warehouse library, all loaded when the dialog opens. It opens on the section looked at last, kept in local storage (`opencalque.librarySection`, like the recent colours), unless that section is no longer offered.

### Starting, About and releases (`Welcome.tsx`, `About.tsx`, `release.ts`)

`startUp` in `actions/file.ts` runs once (the interface is rebuilt on a language change, the app starts once): it opens the file the app was launched with or, without one and with the `showWelcome` preference on, opens the welcome window. Until it has decided, a loading screen covers everything: `#splash` in `index.html`, plain HTML and CSS because the CSP allows no inline script, painted before the main bundle (several megabytes) is read, so a cold start shows the logo and a moving bar rather than a blank window. It is outside `#root`, so React's first render leaves it in place; `hideSplash` (`splash.ts`) takes it away when `startUp` ends, or when `Guard` catches a fault, and `startUp` gives up waiting after eight seconds. Without it, the editor could be drawn on during the moment `startUp` waits for IndexedDB (unsaved work to recover) and the launch file, and the welcome window then covered it. Its colours follow the system until `theme.ts` sets `data-theme`, then the user's theme; the desktop window starts with the same background. The browser tests open the editor with `openEditor` (`e2e/support.ts`), which waits for the splash to let clicks through. The welcome window offers a new drawing, a file, the drawings `platform.recent` lists, and the example, which is `examples/apartment.opencalque` imported as text with `?raw` and only fetched when asked for.

**Versions have one source: `CHANGELOG.md`.** `release.ts` imports it as text and parses it (`parseChangelog`); the newest section gives `VERSION`, and About shows them all. `release.test.ts` fails when any `package.json` of the workspace carries another version (the installers take theirs from the desktop package, `opencalque --version` from the CLI's). Notes are plain text lines, in English, not passed through `t()`; only the headings New, Improved and Fixed are translated.

**Releasing.** Pushing a tag `vX.Y.Z` runs `.github/workflows/release.yml`: each system builds its installer with `electron-builder` (configured under `build` in `apps/desktop/package.json`; the app ships no `node_modules`, everything is bundled into `out/`, so a package the main process uses, `electron-updater` among them, is a devDependency: electron-vite bundles those and leaves `dependencies` outside), then one job creates the GitHub release with the text `scripts/release-notes.mjs` extracts from the changelog. A tag without a changelog section fails before anything is built. The text before the first `###` of a section is the start of the release's description on GitHub, not shown in About. Builds are unsigned. The installers carry `LICENSE.txt` and `THIRD-PARTY-NOTICES.txt` beside the app (`extraResources`). The icon is `apps/desktop/build/icon.png`, rendered from `apps/web/public/icon.svg`. Because `publish` names the GitHub repository, electron-builder also writes `latest.yml` (for the Windows setup), `latest-linux.yml` (for the AppImage) and a `.blockmap` per installer, which the workflow uploads beside the installers, and puts an `app-update.yml` in the installed app saying where to look: these are what an installed app updates itself from.

**Updates** (`apps/desktop/src/main/updates.ts`, `apps/web/src/updates.ts`). The desktop app looks for a newer version only when its window asks: at start when the `checkUpdates` preference is on (the default), and from "Check for a new version…" (Preferences menu, About). The Windows setup and the Linux AppImage replace themselves with electron-updater (`NsisUpdater`, `AppImageUpdater`, made by name rather than through `autoUpdater` so that macOS never gets one; the portable app is told apart by `PORTABLE_EXECUTABLE_FILE`, an AppImage by `APPIMAGE`): the newest release's installer is downloaded in the background, checked against the sha512 its `latest.yml` gives, and installed silently when the app quits. No signature is checked, `publisherName` being unset in unsigned builds. "Restart to update", in the menu bar, closes the windows first, each asking about unsaved changes as on any close, and calls `quitAndInstall` only from `window-all-closed`: it starts the installer before it quits, so calling it while a window could still be kept open would replace an app that is still running. A window kept open (`keptOpen`) leaves the update for the next quit. macOS (which replaces only a signed app), the portable app and an unpackaged run ask the GitHub API for the newest release that is not a pre-release and offer its page; only the version is read from the answer, the address is built from it. When the updater fails (a release without `latest.yml`, as 1.0.0 and the ones before it are), a newer version is still offered that way. The state (`UpdateState`, in `updateState.ts`, which has nothing of the DOM so that the main process can share it) is sent to the window on each change; the menu bar shows a version ready or out, and only a check asked for says in a message what it found. The first version that has this updates only to later ones: someone on 1.0.0 downloads the next one by hand.

**Title bar.** On Windows and macOS the window has no title bar (`titleBarStyle: 'hidden'` with `titleBarOverlay`): `.menubar` is the drag region (`-webkit-app-region`), its buttons opt out, and its padding uses the `titlebar-area-*` CSS environment values to leave room for the system's buttons. The overlay's height in `main/index.ts` must match `.menubar`. Anything placed over the menu bar would not receive clicks where the bar is draggable.

### Units (`units.ts`, `imperial.ts`)

Every length shown or typed goes through `units.ts`, in the unit of the preferences. Feet and inches (`'ft-in'`) are not a number followed by a unit: `formatNumber` returns the whole text (`7' 6 1/2"`, from `formatFeetInches` in the core, rounded to the preference `fraction`), and `parseLength` reads it back with `parseFeetInches`, which is tried for every unit so that `7'6"` is understood anywhere. A bare number typed in feet and inches is feet. Code must therefore never do arithmetic on what `formatNumber` returns. The formatting lives in the core because a dimension can show its length that way (`unit: 'ft-in'`, `fraction`), and `quantitiesCsv` takes `system: 'imperial'`.

**The decimal mark** is a preference (`decimal`: `'auto'`, the language's, or `'.'` or `','`), read through `decimalMark()`: `formatNumber`, `formatAngle` and `formatArea` write numbers with it in the panels (`formatDecimal`, never `Intl` with the language directly). A number is read with either mark (`parseNumber`).

**What the drawing writes belongs to the drawing** (`doc.settings`, `settingsOf` in `document.ts`): `system` (`'imperial'`: rooms in ft², tables in feet) and `decimal`, each stored only where it is not the usual (metric, a point), changed with `set_document`. Rooms, tables of quantities and dimensions read them where they are drawn (`roomArea`, `dimensionLabel`, `tableContent`, all from `ctx.doc`), as does the CSV export. They were once written on each room, table and dimension when placed, from the preferences, and the values of 1.3 drawings still win where they are (scripts may set them too), but the editor writes none and shows no field for them: File › Drawing settings (`DrawingSettingsWindow.tsx`) changes the drawing's with `drawingSettingsOps` (`settings.ts`), which also takes off what rooms, tables, dimensions and dimension styles said of their own, so that the drawing reads one way. A table's words keep `{unit}` where the unit goes (`withUnit` fills it in as it is drawn; `unitless` puts it back in words typed or written by 1.3, at the last place the unit stands alone), so a table follows the system. A new drawing takes the preferences' way (`newDrawingSettings` in `units.ts`, from `blankDocument`). Lengths in the panels stay in the unit of the preferences: that is how one person reads, not what the drawing says.

### Languages (`i18n.ts`, `locales/`)

The English text is the key. `t('Save as…')` returns it in the active language, or unchanged when there is no translation; `{name}` placeholders are filled from a second argument; `tn(count, one, other)` picks a form by count. `msg('…')` only marks a text, for tables built at import time before the language is known (menus, field tables, command titles); whatever displays it later calls `t` on it.

- **Adding a language**: add `locales/xx.ts`, then a line in `LANGUAGES` and `LOCALES`. `i18n.test.ts` scans the source for every literal passed to `t`, `msg` and `tn` and fails if a language is missing one, has a leftover, or changes a placeholder. Texts of two characters or fewer, and those without a lowercase letter ("X1", "mm"), are exempt.
- **Adding a text**: write it in English inside `t()` and add it to each language file; the test tells you which are missing. Only literals are found, so do not build a key by concatenation.
- **Extensions translate themselves**: `Extension.translations` maps language → English text → translation, and `t` falls back to it. Option values such as "Single" are stored in drawings in English; only their display is translated.
- **Changing language** remounts the interface (`<App key={language}>` in `main.tsx`), which is why `t` can be a plain function with no subscriptions. The drawing, history and settings live in stores outside React and survive it.
- **Not translated**: error messages from `@opencalque/core` (they are also read by scripts and by the assistant), the assistant's system prompt, and native file-dialog filter names. Names created in a drawing ("Layer 2", "Reference") are written in the language in use at the time and stay that way.
- The command palette matches the translated name, the English name, and a command's `keywords`, so documentation written in English still works.

### Panels (`dock.ts`, `Layout.tsx`)

The drawing is surrounded by panels managed by `dockview-react`: each can be dragged to an edge, dropped on another to share its tabs, floated, resized and closed. The arrangement is saved to `localStorage` under `opencalque.layout` on every change and restored at start, with titles re-translated. The panels are a stacking context of their own (`isolation: isolate` on `.dock`): dockview gives the handles between panels a z-index of 99, which would otherwise come over every window, menu and message the app lays over them, and take the clicks meant for a dialog where it covers one.

- `dock.ts` lists the panels and exposes `showPanel`, `togglePanel`, `resetLayout` and the `useDock` store of open panel ids. It contains no components, so anything may import it; `Layout.tsx` registers the real implementation when it mounts. Keep it that way, or imports become circular (panels import actions that need to show panels).
- The canvas is a panel too, pinned by `pinCanvas`: it has no tab strip.
- `limitDropZones` vetoes drop zones that would give a useless result (through the library's `onWillShowOverlay` event), so every zone offered while dragging is sensible: on the drawing a panel can dock along a side but never becomes a tab of it, and a column narrower than `SPLIT_MIN_WIDTH` is not offered a side-by-side split, only stacking or sharing tabs. Add rules there rather than fighting the library's defaults elsewhere.
- Panels are dragged with pointer events (`dndStrategy="pointer"`), not the browser's drag and drop: on Windows its cursor said "not allowed" for an instant as a drag began and at every edge between two elements on the way, the browser asking the page too late, and nothing the page does changes the first one. While a panel is dragged, `markDrags` puts the class `dock-dragging` on the page (from `getPanelData()` and the pointer's buttons): one cursor everywhere (`grabbing`), no hover on tabs, and the "···" lets the pointer through to the row under it. The tab that follows the pointer is the library's copy of it in `<body>`, outside `.dock`, styled on its own in `styles.css`.
- `THEME` sets how a drag looks: the tabs stay where they are (`tabAnimation: 'default'`) and a short bar marks where a tab will land, and a panel's area is outlined. `styles.css` turns the library's marks (a line at a tab's edge, a box over the empty part of the row) into that bar, drawn across the boundary between two tabs at the same place whichever of them the pointer is on, without the library's slide (which swept it across a tab as the pointer went onto it); the row does not clip, so the bar after the last tab shows whole. `leavesInPlace` (in `limitDropZones`) shows no bar where a tab would stay where it is; a drop there does nothing. The library's other way, tabs sliding apart around a gap, moved them under the pointer as it went.
- A row of tabs never scrolls. `MoreTabs` (the group header's right actions) measures the tabs at their full width, leaves out whole those that do not fit (class `tab-hidden`), always keeping the one in front, and lists them behind a "···" at the right end of the row; one chosen there comes in front and so into the row. Which ones show is `tabsInView` in `dock.ts`, tested on its own. It fits the row again when the header is resized, when tabs are added, taken away, moved or renamed (a `MutationObserver` on the row, which ignores the drop marks the library adds and takes away while dragging) and when the tab in front changes. The right actions are laid over the end of the empty part of the row, which takes a tab dropped after the last one. The library's own list of overflowing tabs is turned off (`disableTabsOverflowList`), and its scroll bar (`scrollbars="native"`). The close cross has room of its own on every tab and shows only under the pointer, never over the name.
- A panel that did not exist when the layout was saved (`opencalque.layout.panels` lists those that did) is opened behind its `PARTNER` at the next start, so new panels are found without resetting the layout.
- **Adding a panel**: add it to `PANELS` in `dock.ts`, to `COMPONENTS`, `SIDE` and `PARTNER` in `Layout.tsx`, and a `panel('id')` command in `commands.ts`. It then appears in View and in the palette.
- Toggling a panel that is open but behind another tab brings it forward; only a visible panel is closed.
- **Columns keep their width; the drawing takes the difference** (`drawingTakesTheDifference`). Dragging the line between two columns resizes the one on its side away from the drawing, those between it and the drawing keeping theirs; a column closed leaves its room to the drawing (a panel closed among others stacked in a column, to the last of them), and nothing is evened out; one added without a width of its own (dropped on the window's outer edge) takes half of the drawing, as a drop beside it does. dockview gives a drag's change to the nearest view and evens out a whole row when a view goes, with no option for either (a group's `priority` cannot be set, and a drag passes none), so every splitview of the main grid has its `resize`, `addView` and `removeView` wrapped, again after each change of layout for the splitviews made since. These are the library's internals: after updating dockview, run the browser test "resizes a column by its line away from the drawing". Should they have changed, the wrapping does nothing and the library's own way comes back. A resized window still scales every column in proportion (the library's `proportionalLayout`).

### Theme (`theme.ts`)

The `theme` preference is `system`, `light` or `dark`; `theme.ts` resolves it against `prefers-color-scheme`, sets `data-theme` on `<html>` and keeps the result in `useTheme` (`dark`, and `darkCanvas` when the drawing is to be dark too, the `darkCanvas` preference). The interface takes every colour from the variables at the top of `styles.css`, which `:root[data-theme='dark']` redefines: **use a variable, never a literal colour, in new CSS**, or add one to both blocks. On desktop the optional `Platform.setTheme` passes the choice to the window (system buttons, dialogs, background). It is called at start as well as on every change, and says whether the app is following the system: Windows draws the highlight under the minimise and maximise buttons light or dark from `nativeTheme`, not from the colours given to `titleBarOverlay`, so a window left on the system's dark setting under a light interface shows no highlight at all.

The canvas gets a `CanvasPalette` (`LIGHT_CANVAS`, `DARK_CANVAS`, `DARK_AROUND_CANVAS` in `draw.ts`) for its own colours (surface, desk, grid, axes, labels) and an `ink` function every colour of the drawing goes through when painted. On a dark canvas that is `darkInk`: lightness turned over with hue and saturation kept, lines and words held at least 62 % light. It exists only in `draw.ts` (and the in-place text editor): the document, the panels' colour fields and every export keep the real colours, and the assistant's pictures are rendered light.

### Platform seam (`platform.ts`)

`Platform` covers files (`open`, `openBytes`, `save`, `initial`, and on desktop `recent` and `openRecent`), the words of the desktop app's own dialogs (`setDirty`, `setDialogLabels`), and a `desktop` flag with capabilities only the desktop app has: `request` (an HTTP request made by the main process, so a local model server need not accept the page's origin), `claudeCli` and `cancelClaudeCli`, `onOpenFile` (drawings macOS asks the running app to open), `showBackups`, and `checkForUpdate`, `onUpdate` and `installUpdate` (see "Updates" above), and `secrets`, where the keys of the assistant's services are kept: the main process encrypts them with `safeStorage` into `secrets.json` in the profile, by service (`anthropic`, `compatible`, nothing else accepted), and says it cannot (`available`) where Electron would only obscure them (Linux's `basic_text`). At start `keepKeysIn` (`prefs.ts`) reads them into the preferences and moves there a key still written with them; from then on `storedPrefs` leaves keys out and `setPrefs` hands a changed one to the store. The preferences in memory still hold the key, which is what the providers read. Code checks for the capability (`platform.claudeCli`), not for the flag, so a future host can offer some and not others. The browser implementation uses the File System Access API where available and falls back to download. The desktop implementation is the preload script. `token` is an opaque identity for saving back in place (a path on desktop, a file handle in the browser).

On desktop the main process only writes to paths the user picked in a dialog or launched with (`granted`), and the window runs sandboxed with context isolation. The list of recent drawings is kept by the main process (`recent.json` in the profile), and `openRecent` refuses a path that is not on it, so the window cannot read arbitrary files. A link to an `https` address opens in the user's browser; nothing else opens a window, and the window never navigates away from the app (`will-navigate`).

Saving on desktop (`writeSafely`) writes beside the file and renames over it, so a drawing is never half-written; when Windows refuses the rename because another program holds the file for a moment, it retries, then writes in place as a last resort. Before the app first writes over a drawing in a run, it copies it to `backups/` in the profile (`backUp`, the 30 newest kept). `request` reaches localhost freely, and any other origin only after the user said yes in a native dialog (`mayReach`, remembered in `allowed-hosts.json`), so a page that went wrong could not use the main process to reach the network around the computer.

## 6. How to extend

**A new parametric object** (the preferred route for anything describable by parameters): register it in an extension, as `packages/ext-architecture` does. It appears in the object library with a generated properties form (numbers, checkboxes, and dropdowns for string parameters with `options`). No other change is needed. Implement `opening` to make it cut and snap to walls. `build` must tolerate any parameter values the user can type; a `build` that throws is drawn as a placeholder.

**A new command or shortcut**: add an entry to `STATIC` in `apps/web/src/commands.ts`. Extension commands registered through `registerCommand` appear automatically under "Extensions".

**A new built-in node type**:
1. Add its schema to the union in `schema.ts`.
2. Add an entry to `KINDS` in `kinds.ts` (`primitives`, `move`, `transform`, optionally `handles`, `moveHandle`, `snapPoints`, `snapLines`). TypeScript will not compile until this exists. A box that is resized by a frame needs a case in `resize.ts`.
3. Add a label in `TYPE_LABELS` (`ui.tsx`) and fields in `FIELDS` (`panels/properties/fields.ts`).
4. If it needs a tool: add it to `Tool` (and its hints to `hintsFor`) in `tools.ts`, a button to `ICONS` and the `Toolbar` in `Stage.tsx`, a `tool(...)` entry in `commands.ts`, and what it does: a two-point shape is a case of `shape()` in `canvas/shapes.ts`; anything else gets its press in `PRESSES` and, for a gesture of its own, a `Gesture` kind with its move and release (`canvas/gestures/`), and a test in `e2e/tools.e2e.ts`.
5. Run `pnpm schema` and add a test.

**A new operation**: add it to the `Op` type, to `OpSchema`, and to `applyOp` in `ops.ts`. Keep each op to a single node or layer; that is what keeps future merging simple.

**A new extension**: prefer a declarative one, a JSON file in `packages/warehouse/extensions` (listed in `EXTENSION_FILES` in `packages/warehouse/src/index.ts`; `warehouse.test.ts` fails when one is left out). One in code is a package depending only on `@opencalque/core` that exports an `Extension`, used by `loadExtensions` in `apps/web/src/extensions.ts` and by `standardRegistry` in `packages/warehouse`.

**Changing the file format**: see §4, "The file format and its versions". An optional property needs nothing more; a new node type or a changed meaning bumps `FORMAT_VERSION` and adds a step to `MIGRATIONS` in `read.ts`, with a test in `format.test.ts` that opens a drawing of the old version.

## 7. What has and has not been verified

How the project is checked, and what nothing checks yet. What was verified by hand, round by round, before 1.0 is in the history of this file and in the changelog; it is not repeated here.

**Automated, on every push (CI):**

- `pnpm typecheck`, across every package, each with only the types of where it runs (§3).
- `pnpm test` (Vitest, about 480 tests): the core (`packages/core/test`: the file format and repairs, walls, corners and justification, rooms against 200 random plans and the fixtures of real plans, materials and walls of materials, tables of quantities, transforms and resizing, snapping, the clipboard, exports and fonts, 2 000 walls redrawn), the warehouse (`packages/warehouse/test`), and the editor's pure parts (`apps/web/src/*.test.ts`: the assistant's loop against a scripted model, stored conversations, the libraries' places, the dock, coverage of every language, units, a PDF read back by pdf.js, cancelling an export).
- Drawings saved by 1.0 (`packages/core/test/fixtures/drawings`: the two examples as they were, and `every-kind.opencalque`, with every type of node and most of what nodes carry) open with nothing to put right and draw as they did: `drawings.test.ts` compares each page's SVG (and every-kind's DXF) with the files kept beside them. A change in how such a drawing is drawn fails there; if it is meant, look at the difference, accept it with `pnpm test -u`, and say in the changelog what changed for existing drawings. The drawings themselves are never changed.
- `pnpm notices --check`: the licences shipped are those of what the build holds.
- `pnpm e2e` (Playwright, Chromium, the production build with its CSP): `e2e/editor.e2e.ts` (saving and autosave, repairs, a newer file refused, paste, colours and opacity, walls by their faces and ends, openings and stairs stretched, the object library, groups and the breadcrumb, the Structure list, dimensions, panels, a 20 000-line DXF, crash recovery, the assistant against a stand-in API, About and its licences) and `e2e/tools.e2e.ts` (each tool of the canvas and each drag of the select tool, read back from the saved drawing). Every browser test also fails on a script error or a CSP violation (`failOnErrors`).

**Run by hand:**

- No test takes over the screen. The browser tests are headless; `OPENCALQUE_BACKGROUND=1`, which `e2e/desktop.e2e.ts` sets, makes the desktop app show its window off the screen, out of the taskbar and without the focus, and `smoke.cjs` does the same. It is shown rather than hidden because Chromium does not paint a hidden page, and a test should see what a person sees; a test checks that it is. Windows would count a window off the screen as covered, which stops the painting too and hangs `capturePage`, so `CalculateNativeWinOcclusion` is off. The app also does not ask about unsaved changes in this mode: a native dialog comes up on the screen with the focus, wherever its window is.
- `e2e/desktop.e2e.ts` also runs the command Preferences shows, as a terminal would split it, against the built app, and `opencalque mcp --live`: refused until the preference is on, then an edit on the canvas, a picture drawn by the app's browser, the whole edit undone in one step, refused again once it is off. `packages/cli/test/mcp.test.ts` speaks the protocol to a server on a file, and the bridge's rules on tokens and web pages against the real `bridge.ts`.
- `e2e/desktop.e2e.ts` drives the built desktop app on Windows (skipped where it is not built, as in CI): a drawing given on the command line, Ctrl+S with no temporary file left, an unknown property kept, one backup before the first save; the key of the assistant moved into `secrets.json`, encrypted, and read back.
- `pnpm smoke` (`apps/desktop/scripts/smoke.cjs`) drives the built app with real input events at hard-coded positions for a 1400×900 window and writes screenshots to a temp directory. It fails when a step did not leave the objects it should in the Structure list, when the page reports an error or crashes, and after 60 seconds; what looks wrong without being counted is still for a person to see in the screenshots. It loads the page without the preload script, so it exercises the browser platform. `OPENCALQUE_SCREENSHOT=<file.png>` makes the real app save one screenshot two seconds after load and quit.
- `pnpm rooms:gallery`, `pnpm walls:gallery` and `pnpm warehouse:gallery` draw the plans rooms are tested on, every way walls built of layers meet with random plans of them, and every bundled symbol, to look them over; `pnpm dist` builds the installer for the system it runs on.

**Not verified, treat as untested:** the macOS and Linux packages beyond CI building them, `open-file` on macOS, installing through the setup program, and so an update installed by it (finding a newer version and downloading it were run in the packaged Windows app against a local feed, and the portable app's question to GitHub against the real one; the install itself was not, as it would have replaced the app installed on that computer), an AppImage updating itself; the fallback that writes in place when Windows refuses a rename, the connection question for `request`, the recent-files list in a real session; the real Claude Code CLI (its JSON shape and keeping sessions per folder are assumed from its documentation), a real Ollama model, the OpenAI-compatible provider beyond a stand-in, the assistant against the real Anthropic API, resuming a stored conversation there, `view_image` with a real model, how well a model traces a plan; Adobe Reader and macOS Preview for exported PDFs, a DXF from another CAD program and the exported DXF opened in one (Chinese text in AutoCAD included), papers in SVG and DXF exports, scaled instances and rotated ellipses in DXF; curved walls of layers, with round, bevel and butt joints and in exports; snapping and smart guides in drawings with thousands of objects, and with walls, groups and papers; rooms in angled plans and inside components on screen; crops on walls, instances and pictures on screen; transforming doors and windows in walls (they do not re-attach); the eyedropper itself (Playwright cannot drive `EyeDropper`); a real drag from the file manager (the events were synthesised); pasting between two windows through the system clipboard, and a picture pasted from another program in the desktop app (the browser tests write one to Chromium's clipboard); floating panels and very narrow windows; PDFs with unusual fonts or several pages; the palette on macOS (Cmd), resetting shortcuts and the message when a key is taken from another command; most property-panel edits one by one, the PDF export window, installing an extension from a file, switching the built-in extension off, a web catalog on a real host; the quality of the translations (no native speaker has reviewed any of them).

A scripted run needs no care from whoever is at the computer: its window is off the screen, so the cursor cannot reach it. Electron's `capturePage` used to stall now and then, most likely when Windows counted the window as covered, which `CalculateNativeWinOcclusion` being off prevents.

## 8. Decisions and their reasons

| Decision | Reason | Revisit when |
| --- | --- | --- |
| Web app first, desktop as a thin shell | The owner may host it later; keeps the shell replaceable | — |
| Electron, not Tauri | Same Chromium everywhere (canvas behaviour, File System Access API); contributors need only JS tooling. Cost: ~100 MB installers | Installer size becomes a complaint; only `apps/desktop` would be rewritten |
| Flat node map, `parent` + fractional `order`, no child arrays | Concurrent edits merge per node, last writer wins; no redundant structure to keep consistent | — |
| Single-node JSON operations as the only mutation path | One stream serves UI, undo, CLI, extensions, AI agents and future sync | — |
| Undo by keeping whole documents | Simple and correct; structural sharing makes it cheap | Collaboration arrives: undo must then be per-user and op-based |
| Each undo step keeps the operations that made it (`Step` in `store.ts`) | One stream of operations, through one function (`record`), for a sync layer to send; no inverse operations needed yet | Collaboration: undo becomes per-user and op-based |
| Each package compiled with only the types of where it runs | The core must stay usable by the CLI, a server and workers; the compiler, not a rule in a file, keeps it free of the DOM and of Node (`host.ts` says what it takes from its host) | — |
| What ships is a package (`packages/warehouse`) | The editor, the CLI and a server draw the same objects from the same files | — |
| Everything renders through primitives | New object types get rendering, selection, snapping and export for free | A kind needs something primitives cannot express (hatches, images) |
| Parametric objects are one node type with a `kind` string | Files using unknown extensions still load and round-trip | — |
| Canvas 2D, the drawing kept in a canvas of its own, stretched while the view moves | Fast enough for plans of a few thousand objects; no renderer complexity | Drawings reach tens of thousands of objects: cache scene items per node, then consider WebGL |
| Zod 4 schemas as the source of truth | Types, validation and published JSON Schema from one definition | — |
| `z.config({ jitless: true })` in `schema.ts` | Zod otherwise probes `eval`, which the CSP reports | — |
| No library build step | Less tooling while the API is moving | Publishing `@opencalque/core` to npm |
| Assistant calls the provider directly from the app, with the user's key | No server needed for a local app; the provider seam leaves room for a server-side one | The hosted version: keys must stay on a server |
| Assets inside the JSON file, as base64 | One self-contained file, still plain JSON | Files get large: move to a zip container holding the JSON and the binaries |
| MIT licence | Confirmed by the owner for 1.0 (October 2026) | — |
| Installers stay unsigned | The owner's choice for 1.0: no certificate is bought. macOS gets an ad hoc signature so that Apple-silicon Macs open it; Windows shows SmartScreen's "More info" step. ## 9. Known limitations and rough edges

- Installed extensions do not update themselves. A library's texts are translated only when its catalog entry carries `translations`.
- A declarative extension can add objects but not tools, commands or panels.
- DXF export writes separate lines rather than polylines. Walls are written as one outline: each edge is cut where other walls cross it and the parts inside or along another wall are dropped (`outside` in `dxf.ts`), which is quadratic in the number of walls.
- Snapping treats a group as what it draws: the faces of walls inside a group can be snapped to from outside it, their middle lines cannot. Circles and ellipses give their centre only: no quarter points, no tangents, and no nearest point on a whole circle.
- Openings are linked to walls by position only; they follow a straight wall an edit changes (see §4, Openings), not yet a curved one.
- A wall ending on another wall's body is cut along its face only when its end is in that one wall; at a corner of two others it overlaps them, as before.
- Walls of materials: a lining is drawn by hand against its wall and does not follow it when the wall is moved or made thicker; a door or window goes through walls laid against its own, but its frame is drawn as deep as its own wall.
- Tables of quantities count one page each; their rows can be chosen one by one, but not by a rule (one layer, every door), and they have no sorting of their own and no mark drawn beside what they count on the plan; their column widths are estimated. A row chosen by a name (a room, a material) is lost when that name changes.
- Objects are solid: for an `instance` or a `parametric` node, `nodePrimitives` puts a white, strokeless copy of every closed shape that has no fill under all of the node's lines (`OBJECT_FILL`), so what lies beneath does not show through and no shape of the object hides another's lines. Open shapes (a door's swing) stay see-through, and so does a shape filled with `'none'`, which the fill window writes when None is chosen inside a component; in a see-through group the backing is faded with the group (`faded`). It is `objectBacking` in `kinds.ts`. A component being edited is drawn the same way (`placedScene`, only on the canvas: the scene itself, which exports and snapping read, has no backing), so that what is white or see-through there is so where it is placed; what is on every sheet is not, since papers draw it unbacked (`drawnSolid`).
- Picking (`hitTest`): a component instance or a parametric object is hit anywhere inside one of its closed shapes, filled or not (`insidePrimitive`); other nodes by their lines and fills. Floors (`backdrop: 'floor'`, with their hatch) are never hit: a room is picked by its name. An object made only of open lines (a door's leaf and arc) is still picked by its lines.
- Stairs have no break line, handrails or winders; the L and U landings are square.
- Dimensions are linear and aligned to their two points only: no horizontal/vertical-only, angular, radius or chained dimensions, and they do not follow the geometry they measure. Text width is estimated, so the gap for on-line text is approximate. Fonts are limited to generic families available without downloads.
- Dimension tool defaults are not persisted between sessions.
- Imported plans cannot be straightened, one PDF page is read at a time (asked with a plain prompt), and each plan adds up to a few megabytes of base64 to the file.
- An agent on a file has no undo, and nothing stops it and the app writing over each other: `--live` is the way to work on what is open. The server on files runs from a checkout only: the app does not hold it, `@opencalque/cli` is not published, and its `bin` is TypeScript, so publishing it needs a build first. Live mode is the desktop app's: a browser cannot listen on a port. `--mcp` was run on the packaged Windows app, with the fuses on, by Claude Code; on macOS and Linux it has not been run at all.
- `checkDrawing` looks at plans, not at what they mean: it says nothing of furniture in a doorway or a room of the wrong size. A model sees those in `view_drawing`.
- The assistant edits without asking first (undo is the safety net) and shows replies as plain text. The whole drawing is resent with every request up to 40 000 characters, which costs tokens on large drawings.
- In the web app, API keys are stored unencrypted in localStorage, as the browser offers nothing better. The desktop app keeps them encrypted (see Platform seam).
- A Japanese drawing written only in kanji, exported from an interface in another language, gets the Chinese forms of its kanji, and so does a Korean one written only in hanja. Bold in the embedded fonts is the regular font outlined, and every family (serif, monospace) uses the same sans-serif face. The web app downloads 13.7 MB the first time a PDF needs Chinese, 7.5 MB the first time one needs Korean.
- Translation covers the interface only; see Languages above for what stays in English. Right-to-left languages are not supported by the layout.
- Panel content is not responsive to very narrow panels. Pages, Layers and Components keep a heading under their tab because it carries their buttons; Structure has none.
- Shortcuts are single key presses with modifiers: no chords (`G` then `P`). Extensions cannot declare default shortcuts yet.
- Some defaults are awkward on non-US layouts (for example `[` and `]` need AltGr on AZERTY); they can be rebound.
- Curved walls cannot be drawn directly, extended, trimmed or given a dimension chain (see Curved walls).
- Smart guides apply to moving only, not to drawing or resizing, and line things up by their upright boxes.
- A text's hit box is estimated from character count; text has no alignment or bold of its own.
- No viewports: a paper cannot show part of the plan at another scale.
- Installers are unsigned (a decision, see §8). The Windows setup and the AppImage update themselves; macOS and the portable Windows app are only told of a new version and offered its page ("Updates", §5). The macOS app is signed ad hoc by `apps/desktop/scripts/after-pack.cjs` (an `afterPack` hook), which is what keeps Apple-silicon Macs from calling it damaged; it is not notarised, which needs a paid Apple developer account. On macOS a drawing opened from the Finder comes through the `open-file` event (queued until the window listens, then read once by `file:openRequested`); on Windows and Linux the path comes as an argument, and a second file starts a second window.
- Instances have no overrides (per instance values of what is inside, a different text or size); their colour comes from their layer. A detached instance's objects are no longer solid (see above): only instances and parametric objects hide what lies under them.
- Extensions are compiled in; there is no runtime loading or permission model.
- `scene` is rebuilt for the whole container on every change. Walls no longer scan each other: for each state of the drawing, `walls/spatial.ts` indexes wall ends by square millimetre and walls by the square metres they cover (`wallIndex`, `openingIndex`, keyed on `doc.nodes`, the layers and `registry.version`), so 2 000 walls with 1 000 doors build in about 0.1 s. Each node's primitives are still recomputed on every change; caching them per node is the next step for drawings of tens of thousands of objects.
- The dark theme changes only how things look on screen; a picture imported as a plan is drawn as it is, so a white scan stays white on the dark canvas. The app menu is removed on desktop, so macOS has no standard menu bar; closing the window quits on every platform.
- The name "OpenCalque" is used by unrelated projects; check before publishing.

## 10. Suggested next steps

What 1.0 leaves for later, in rough order:

1. **Speed on large drawings**: each node's primitives are still recomputed on every change (§9). Caching them per node, invalidated by what a node depends on (its walls for a room or an opening, its component for an instance), is next; then the canvas, which paints the whole drawing again when it changes (it keeps it otherwise); and the Components panel, whose rows are all drawn again at each selection.
2. **Openings**: they follow straight walls (`openingFollowOps`); curved walls are next. Also trim walls that end on another wall's body, and make the opening area clickable.
3. **Drawings that carry the declarative extensions they use** (an open question for the owner): they are data, so a drawing could hold the definitions of its objects, as a PDF holds its fonts, and open the same on a computer that does not have them installed. An optional property, no version bump.
4. **More browser tests**: the property panel field by field, the PDF export window, the dock layout.
5. **Runtime extensions**: load from a folder, sandboxed (a Worker with a message API mirroring `ExtensionApi`).
6. **Packaging**: updates that install themselves on macOS, which needs signed builds (§8); Windows and Linux have them.
7. **Hosted version**: see below.

### Path to collaboration and hosting

Nothing is built, but the model was shaped for it. The intended route:

- A server holds the authoritative document and an ordered log of operations per document.
- Clients send ops; the server validates with `parseOps` + `applyOps`, assigns a sequence number, and broadcasts. Conflicts resolve last-writer-wins per node property, which the flat map and single-node ops already allow. Fractional `order` keys mean concurrent inserts do not collide.
- The client hook is `record` in `store.ts`: every committed change passes through it with the operations that made it (`Step.ops`), whether it came from `apply`, from `commit` after a gesture's previews, or from the assistant. `preview` stays local.
- Storage and accounts go behind a third `Platform` implementation.
- Things to design at that point: per-user undo, presence (cursors, selections), `update_node` granularity (it currently replaces whole top-level properties such as `a` or `props`), and what happens when two clients edit the same component.

A CRDT library (Yjs, Automerge) is the alternative if offline-first peer merging becomes a requirement; the server-ordered approach is simpler and matches how Figma works.
